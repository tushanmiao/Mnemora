# 先有证据，再下结论

## 核心原则

**结论之前必须有证据，没有例外。**

绕过字面规则就是绕过规则本身。换个说法表达同样的意思，同样算违反。

## 铁律

```
没有当场取回的证据，就不能下结论
```

如果你在这条回复里没有真的读过来源，你就不能说"有来源支撑"。
如果你没有逐条对照过大纲，你就不能说"全部覆盖了"。

## 检查关

```
在下任何结论、或表达任何满意之前：

一、确认：什么证据能支撑这个结论？
二、取回：真的去取——knowledge_read 读原文、web_fetch 抓页面、
        note_read 读回自己写的内容、workspace_read 读文件
三、通读：完整读，不要只看标题和摘要
四、核对：证据真的支撑这个结论吗？
   - 不支撑：如实说明实际情况，并附上证据
   - 支撑：下结论，同时附上证据
五、这时才可以下结论

跳过任何一步，就不是核实，是编造
```

## 常见的偷懒

| 想说的话 | 必须先做 | 不够格的替代 |
|---|---|---|
| 这个说法有来源支撑 | 取回原文，找到对应那句 | 记忆里"好像读到过" |
| 笔记覆盖了全部要点 | 逐条对照大纲打勾 | 篇幅够长、看起来完整 |
| 数据是准确的 | 回到原始表格/页面核对 | 上一轮算过一次 |
| 引用的页码/章节没错 | read_pdf_pages 翻到那一页 | 按目录推算 |
| 这个链接是有效的 | web_fetch 真的抓一次 | 域名看着像对的 |
| 用户的问题已经答完 | 逐条回看用户提的每一问 | 答了主要的那个 |
| 已经按反馈改好了 | note_read 读回改后的内容 | 发出了修改动作 |

## 危险信号——停下

- 用了"应该""大概""看起来""据我所知"
- 还没核实就先表达满意（"好了""搞定""完美"）
- 准备把笔记交付给用户，但没有回读一遍
- 直接采信别人（或另一个执行者）的自述摘要
- 只核对了一部分就推及全部
- 心想"就这一次没关系"
- **任何暗示"已完成、已正确"却没有实际取证的措辞**

## 常见的自我说服

| 借口 | 事实 |
|---|---|
| "应该没问题" | 那就去核实 |
| "我很确定" | 确信不是证据 |
| "就这一次" | 没有例外 |
| "大纲列了就等于写了" | 列了不等于写了 |
| "执行者说完成了" | 独立核实 |
| "内容太长了懒得回读" | 长度不是借口 |
| "抽查一部分够了" | 部分证明不了整体 |
| "换个说法就不算违反" | 看精神，不看字面 |

## 典型场景

**引用来源：**
```
✅ knowledge_read 取回原文 → 找到支撑那句 → "根据《X》第 3 节：……"
❌ "有研究表明……"（没取回、没出处）
```

**覆盖度：**
```
✅ 回读大纲 → 逐条在成稿里找到 → "8 个要点全部覆盖" / "第 5 点没写，原因是……"
❌ "已经系统地讲清楚了"
```

**事实与数字：**
```
✅ 回到原始材料核对数字 → 引用时标明出处和日期
❌ 凭印象写出一个具体数字
```

**交付前：**
```
✅ note_read 读回成稿 → 检查术语一致、无占位符、无重复 → 再交付
❌ 写完直接说"完成了"
```

**别人的产出：**
```
✅ 执行者返回 → 实际读他产出的正文 → 抽查事实 → 汇报真实状态
❌ 采信他的自述摘要
```

## 什么时候适用

**在以下动作之前，一律先取证：**

- 任何形式的"完成了""核实过了""覆盖了"
- 任何表达满意的措辞
- 任何关于内容质量的正面判断
- 把笔记交付给用户
- 进入下一节、下一个任务
- 采纳另一个执行者的产出

**规则覆盖：** 原话、同义改写、暗示完成的表达、以及任何让用户以为"这件事已经妥了"的说法。

## 说不清就直说

取不到证据时，正确做法是说明取不到，而不是绕过去。
"这一点我没有找到可靠来源，先标记出来"——这句话永远好过一个编造的引用。
知识笔记里，空缺可以补，错误会被反复读到。
