# 06 工具与技能系统

> 2026-08-23 同步：内置 Skill 已从“改写后的单文件说明”升级为完整官方目录。`SKILL.md` 及上游 references、scripts、assets 保持原样；`mnemora.json` 只保存 Mnemora 的 ID、触发词、模式、默认状态、Tool 依赖和固定 Commit。脚本进入资源包不等于获得执行权限，运行仍受静态 Tool 注册表、权限模式和审批链约束。

## 6.1 概念入门

工具（Tool）是模型可以请求的一次结构化动作，例如读取 PDF 页或搜索记忆；技能（Skill）是可复用的工作说明和提示模板，例如“论文研究”或“代码审查”。工具做事，Skill 说明如何做。Mnemora 将二者拆开：固定工具注册在 Rust，Skill 以带 YAML Front Matter 的 `SKILL.md` 文件安装和解析。

## 6.2 Tool 注册表

`src-tauri/src/chat/agent/catalog.rs::TOOL_ENTRIES` 是静态注册表。每个 `ToolEntry` 包含名称、说明、JSON Schema、命名空间、处理器、风险、只读标记、并发安全、审批策略、资源成本和结果字符上限。命名空间包括 Discovery、Skill、Attachment、Document、Memory；处理器枚举避免动态代码注入。

当前内置工具：`search_tools`、`search_skills`、`skill`、`read_attachment_text`、`read_pdf_pages`、`read_docx_blocks`、`read_xlsx_rows`、`memory_read`、`memory_search`、`memory_modify`。`find_tool` 只从固定表返回条目，未知名称无法执行。

每个 Schema 使用 `additionalProperties: false`，并在 `registry::validate_tool_arguments` 中二次检查类型、字段白名单、长度、范围和资源 ID。这是“模型输出是敌对输入”的基本原则：不能因为 JSON 看起来合法就直接访问文件或记忆。

## 6.3 渐进式披露

目标是降低上下文和前端内存，而不是把 12 个工具的完整 Schema 每轮发送。`build_runtime_context` 首先根据消息附件、记忆开关和已激活 Skill 计算 `available_tool_names`；`configure_model_request` 只放入 `search_tools`、`search_skills` 或当前必需的 `skill`。模型调用 `search_tools` 后，`apply_tool_disclosures` 只把命中的工具契约加入下一轮；搜索 Skill 同样只返回名称/说明，不加载正文。

因此当前实现是**应用层渐进式披露**（Progressive Disclosure），不是 Anthropic/OpenAI 原生 `defer_loading` 协议。模型供应商仍可能收到当前轮已披露的工具完整契约；原生 Tool Search、远端索引和 MCP 动态连接仍是规划项。

测试 `tool_contracts_are_disclosed_only_after_catalog_search` 证明初始只有 `search_tools`，搜索 PDF 后才出现 `read_pdf_pages`，未命中的 `memory_search` 不会出现。

## 6.4 Skill 文件格式

`src-tauri/src/skills/parser.rs::parse_skill` 读取 `SKILL.md`：

```markdown
---
name: paper-research
description: 论文研究辅助
version: 1.0.0
triggers: [/paper]
metadata:
  mnemora:
    source-repository: https://github.com/...
    source-revision: <40 位提交哈希>
    adapted: true
    supported-modes: [chat, work]
    risk: low
    resource-cost: medium
    required-tools: [read_pdf_pages]
---
正文说明，可使用 $ARGUMENTS
```

解析结果 `SkillSummary` 只含 ID、名称、描述、版本、来源、风险、成本、触发器、工具要求、许可证、来源哈希等轻量元数据；`SkillDetail` 在用户打开详情时才读取正文和文件目录。`content_hash` 用于回答中的 ActivatedSkillSnapshot，让以后能知道当时运行的是哪一版。

解析约束包括：SKILL.md 最大 256 KiB；ID 最多 160 字符且仅允许稳定字符；触发器必须以 `/` 开头；推荐/必需工具最多 32 个并逐个校验名称；来源元数据必须满足内置 Skill 的可审计要求。解析不执行 Skill 中的脚本。

## 6.5 Skill 仓库与安装

`SkillRepository::list` 扫描内置目录和用户目录，读取 `skill-state.json` 的启用状态；用户状态覆盖默认启用值。`get_detail` 按 ID 加载单项详情，`set_enabled`、`uninstall`、`restore_builtin` 修改状态或恢复资源。写状态使用临时文件、同步和替换。

`skills/installer.rs::import` 支持普通目录和 ZIP。先复制到 UUID staging，再要求恰好一个 `SKILL.md`，解析和校验成功后原子 rename 到用户目录。拒绝符号链接、路径越界、`.git/node_modules/target`，并限制：压缩包 20 MiB、解压总量 50 MiB、单文件 10 MiB、文件数 512、目录深度 8。用户 Skill 不能覆盖同 ID 内置 Skill。

用户明确要求允许从任意资源库安装，但“允许安装”不等于“自动获得 OS 级执行权”：当前 Skill 仍只能调用 Mnemora 固定注册的业务工具；没有 Shell/网络任意执行处理器。若未来增加可执行扩展，必须另建沙箱、权限和签名策略。

## 6.6 激活方式和上下文注入

手动激活的 Skill ID 在请求验证时校验；斜杠触发器由 `resolve_user_content` 只在请求边界剥离，例如 `/summary 请总结` 变成“请总结”，不会修改已保存的原始用户消息。`render_activated_skills` 将启用 Skill 正文包在 `<mnemora_skill>` 边界中注入系统提示，并隐藏来源 URL/提交哈希，避免把供应链元数据当指令。

一次请求最多激活 12 个 Skill，注入总量最多 192 KiB。模型调用 `search_skills` 后只能看到轻量目录；调用 `skill` 才加载完整正文。`SkillRunCache` 保证同一运行中重复加载只返回“已加载”，不重复增长上下文。

## 6.7 Tool 与 Skill 的执行链

```text
请求附件/设置
  -> build_runtime_context 计算可用目录
  -> 初始只披露发现工具
  -> search_tools/search_skills
  -> apply_tool_disclosures 加载契约
  -> 模型发出 ModelToolCall
  -> find_tool + Schema/字段/资源校验
  -> requires_approval
  -> execute_tool / execute_skill
  -> 有界 ToolExecution(content, preview, truncation)
  -> ToolResult 回到模型；SkillActivated/ToolTrace 发到前端
```

## 6.8 文档和记忆工具的边界

附件工具只接受当前会话中的 `StoredChatAttachment.id`，不接受任意文件系统路径。PDF 按页读取并产生 `[PDF:<id>#page=n]` 引用；DOCX 按内容块读取；XLSX 按工作表和行范围读取。记忆工具只能访问 L1/L2，且受 `MemorySettings.enabled/allow_model_read/allow_model_write` 和会话权限双重控制。`memory_modify` 的 replace/remove 需要唯一匹配，禁止写凭据或外部指令。

## 6.9 结果上限和并发权衡

工具预览最多 2000 字符，文本读取最多 2000 行/32 KiB，PDF 12 页，Office 200 行/块，内存读取 32 KiB。上限防止工具把大型文档一次性复制到模型上下文；代价是复杂任务需要多轮读取。只读附件文本可并行，PDF/Office 解析保持串行以控制 CPU、文件句柄和内存。

## 6.10 前端渐进展示

Rust 发送 `skillActivated` 和 `toolTrace` 事件，`useStreamingRun` 写入消息元数据，`workflowProjection` 只从真实 reasoning/Skill/Tool 生成过程项。普通 Chat 不显示虚构流程；完成后过程默认折叠但可展开。该 UI 改动属于工作区未提交状态，后端事件合同已实现。

## 6.11 测试证据

`skills/parser.rs` 测试 Front Matter、模式/风险/来源、危险 ID 和标准工具元数据；`skills/repository.rs` 测试默认启用、斜杠参数和内置 12 项技能审计；`skills/installer.rs` 测试目录安装/卸载；`chat/agent/registry.rs` 测试渐进披露、参数拒绝、Skill 单次加载和激活上限。

## 6.12 事实状态与未来演进

- **已实现**：固定 Tool Registry、Skill Markdown 解析、目录/ZIP 有界安装、启用状态、按需正文、应用层渐进披露、审批和有界结果。
- **部分实现**：Skill 是提示和资源规范，不是独立进程；不可信 Skill 仍能影响模型提示，因此不能宣称完全沙箱。
- **规划中**：兼容 Anthropic/OpenAI 原生 Tool Search + `defer_loading`；远程扩展市场；不可信可执行 Skill 的 Worker/权限隔离。

## 6.13 零基础学习和面试表达

学习顺序：JSON Schema -> Rust 枚举/trait 与错误处理 -> 文件路径安全 -> 异步任务和取消 -> Prompt 注入边界。面试时可说：“我把 Tool 定义为有 Schema、风险和审批策略的静态条目，把 Skill 定义为可审计 Markdown 包；初始只给发现工具，命中后才披露具体契约，正文按需加载，并对导入、参数、结果和激活总量设硬上限。”
