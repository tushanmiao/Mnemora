# 深度笔记超时、取消与上下文治理修复

## 1. 文档目的

本文记录一次围绕深度笔记和超长对话的系统性修复。修复不是单纯更换加载文案，而是同时调整模型请求生命周期、Token 预算、长会话分析管线、普通 Chat 压缩策略和进度可观测性。

本次处理的四个核心问题是：

1. 深度笔记长时间停在“建立输入快照与语义计划”，用户无法判断是在工作、重试还是已经失效。
2. 普通 Chat 和深度笔记都可能把超过模型上下文窗口的请求直接发给供应商。
3. 深度笔记曾以单次大请求分析完整会话，超长会话只能截断、失败或反复发送相同的大请求。
4. 普通 Chat 的旧压缩触发条件和单次压缩方式无法稳定处理超长消息及超长会话。

修复目标遵循以下边界：

- 不自动替换用户选择的模型或 Provider。
- 不静默截断来源，不把部分覆盖伪装成完整覆盖。
- Skill、Tool、重试、进度和来源覆盖只展示真实运行状态。
- 用户取消后要中断当前网络等待，而不是只在章节结束后检查一个布尔值。
- 在控制内存和请求体体积的同时，不能以明显卡顿或不可恢复为代价。

## 2. 问题现象与根因

### 2.1 “建立输入快照与语义计划”长时间不动

旧界面只知道管线处于 `analyzing` 阶段，不知道当前模型请求的内部状态。因此下面这些完全不同的情况会显示成同一句话：

- 正在读取输入快照。
- 正在等待第一次模型响应。
- 请求已经超时，正在等待退避重试。
- Provider 连续失败，正在重复发送相同的大请求。
- 模型返回了无法解析的 JSON，正在进行结构修复。
- 用户已经点击取消，但当前 HTTP 请求尚未结束。

根因是前端只有粗粒度 Phase，没有请求序号、重试次数、开始时间、退避时间和最近错误；后端非流式调用也没有接收外部取消令牌和单次调用超时。

### 2.2 相同大请求可能被重复发送

深度笔记 Planner 原来直接把完整会话发送给模型。若请求因为网络、Provider 或上下文长度失败，通用重试层会再次发送完全相同的 Payload。对于已经过大的请求，这种重试没有改变失败条件，只会增加等待时间、费用风险和用户的不确定感。

此外，网络失败与 JSON 解析失败原本缺少清晰边界。正确语义应当是：

- HTTP 请求失败：没有可供解析的响应，不能进入 JSON 修复。
- HTTP 请求成功但 JSON 无效：可以追加严格 JSON 约束，再进行一次结构修复调用。
- 大请求超时、连接失败、Provider 失败或上下文过长：直接缩小请求，切换到分块知识账本流程。

### 2.3 取消不能穿透到正在等待的网络请求

旧管线主要在章节或阶段边界检查取消状态。若模型请求正在等待 5 分钟，点击取消后仍可能继续等待到请求返回或超时。

本质问题是取消状态没有贯穿以下完整调用链：

```text
界面取消按钮
  -> Tauri 取消命令
  -> 活动深度笔记运行注册表
  -> CancellationToken
  -> 非流式模型调用
  -> 当前 HTTP Future / 超时 Future / 重试退避等待
```

### 2.4 上下文控制只看“总窗口比例”

模型上下文窗口并不全部属于输入。至少需要同时容纳：

- System Prompt。
- 对话消息。
- Tool Schema。
- Tool Call 和 Tool Result。
- 图片输入的视觉 Token 估算。
- 本轮最大输出。
- Tokenizer 误差、Provider 包装字段和协议差异所需的安全余量。

旧版前端以“达到上下文窗口的 90%”作为自动压缩触发条件。这意味着输入已经占用 90% 后，仍未明确给输出和安全余量留出空间。即便前端判断可以发送，Provider 仍可能返回 `context_length_exceeded`。

### 2.5 深度笔记的字符截断会破坏完整性

旧流程存在 300,000 字符上限。超过部分被截掉后，模型和用户都无法知道哪些消息没有进入分析。这样产生的笔记可能看起来完整，实际只覆盖会话前半部分。

字符数也不是可靠的上下文单位。英文、中文、代码、JSON 和不同模型 Tokenizer 的比例不同，因此必须把字符上限改成显式的 Token 预算和覆盖率。

### 2.6 单次压缩无法处理超长单消息

普通 Chat 原来的压缩请求会一次发送所有候选历史。若单条用户消息本身已经很长，简单地按消息数组分组仍无效，因为这一条消息就可能超过模型输入预算。

同时，逐字符反复估算整个字符串会形成近似平方级开销。超长文本可能让 WebView 主线程出现明显卡顿。因此分段算法必须是线性扫描，并按消息、段落、字符三级退化。

## 3. 总体修复架构

修复后形成两层保护：

```text
前端预算与预处理
  ├─ 普通 Chat：估算可用输入预算，必要时分块压缩
  ├─ 深度笔记：展示预算、分块和覆盖进度
  └─ Context Usage：按可用输入而不是总窗口显示
                 |
                 v
Rust 运行层硬校验
  ├─ 最终请求成形后重新估算
  ├─ 包含 System、消息、Tool Schema、工具结果和图片估算
  ├─ 预留最大输出与安全余量
  └─ 超预算返回 ContextLengthExceeded，不切换模型
```

前端负责尽早发现和处理，Rust 后端负责最终兜底。不能只依赖前端，因为请求在 Rust 层还可能注入 Tool、Skill、Memory 和 Agent Runtime Prompt；也不能只依赖后端，因为等到发送前才报错会让长对话缺少自动压缩体验。

## 4. 修复一：深度笔记请求生命周期

### 4.1 可配置的执行上下文

非流式模型调用新增 `CompleteExecution`，允许调用方传入：

- `CancellationToken`：控制当前请求和后续工具执行的真实取消。
- `max_retries`：使用任务启动时保存的重试快照，不受运行中设置变化影响。
- `attempt_timeout`：限制每次 HTTP 模型调用的等待时间。
- `on_progress`：接收请求开始和重试退避事件。

普通 Chat 的原有 `complete` 接口仍然保留，由它创建默认执行上下文；深度笔记使用 `complete_with_execution` 注入自己的取消、超时和进度规则。

### 4.2 超时规则

当前规则按预计输出规模区分：

| 调用 | 单次超时 |
| --- | ---: |
| Planner、来源分块提取、JSON 修复 | 240 秒 |
| 较大章节生成或修订 | 360 秒 |

超时只终止本次 Attempt。是否重试由错误分类和任务快照中的重试设置共同决定。

### 4.3 重试规则

用户当前默认自动重试为 5 次。这里的“5 次”指第一次请求失败后最多再尝试 5 次，因此界面显示的最大请求次数是 6。

重试只处理可恢复错误，例如限流、连接失败、超时和部分 Provider 临时错误。认证失败、无效配置、内容过滤、用户取消等错误不会进入盲目重试。

重试等待使用同一个取消令牌：

```text
请求失败
  -> 计算 Retry-After 或指数退避
  -> 同时等待“取消令牌”与“退避计时器”
  -> 用户取消：立即结束
  -> 计时器先结束：进入下一次 Attempt
```

### 4.4 Planner 的特殊规则

Planner 第一次直接分析完整会话时，网络重试次数强制为 0。原因是这个请求本身可能太大，重复发送相同 Payload 无法解决根因。

第一次直接 Planner 的结果分为三类：

1. 成功且 JSON 合法：直接进入提纲确认。
2. 成功但 JSON 非法：追加严格 JSON 约束，进行结构修复。
3. 超时、连接、Provider 或上下文长度错误：清空直接规划的临时覆盖状态，切换到小分块知识账本。

用户取消不属于第三类，不会错误地触发分块或 JSON 修复。

### 4.5 真实取消

当前模型调用使用 `tokio::select!` 同时等待：

- Provider 请求完成。
- `CancellationToken` 被取消。

取消令牌也传入 Tool 执行和重试退避等待。深度笔记停止后：

- 尚未产生提纲时，任务进入 `cancelled`。
- 已完成部分章节时，已完成内容保留并可组装为草稿。
- 未完成章节不会被标记为成功。
- 当前网络等待不再继续占用完整超时时间。

## 5. 修复二：统一 Token 上下文预算

### 5.1 后端硬预算公式

已知模型上下文窗口时，Rust 运行层使用：

```text
required_tokens = estimated_input_tokens
                + output_reserve_tokens
                + safety_margin_tokens

safety_margin_tokens = max(4096, context_window_tokens / 12)
```

只有 `required_tokens <= context_window_tokens` 才允许发送。

`estimated_input_tokens` 包含：

- System Prompt 文本。
- 每条消息正文和消息结构开销。
- Tool Call 参数。
- Tool Result 正文。
- 最终披露的 Tool 名称、描述和 JSON Schema。
- 每张图片 1,200 Token 的保守本地估算。

校验位置位于请求最终成形之后，因此 Agent Runtime Prompt、Skill 内容、Memory 和 Tool Schema 不会绕过预算检查。

### 5.2 估算策略

为避免引入常驻 Tokenizer 和额外内存，当前采用轻量估算：

```text
ASCII Token ~= ceil(ASCII 字符数 / 4)
非 ASCII Token ~= 非 ASCII 字符数
```

它不是供应商官方 Tokenizer 的精确结果，因此仍保留至少 4,096 Token 的安全余量。供应商真实用量可继续作为前端上下文显示的锚点，但发送前不能只依赖历史实报值。

### 5.3 模型上下文来源

上下文窗口按以下优先级解析：

1. 用户在模型配置中显式填写的 `contextWindowTokens`。
2. Mnemora 内置模型数据库的上下文窗口。
3. 两者都没有时为未知。

未知不会伪造一个“模型真实支持值”，也不会自动切换模型。普通 Chat 无法执行精确后端硬校验；深度笔记则采用 8K 输入预算进行保守分块，并在 Provider 拒绝时展示真实错误。

### 5.4 超预算错误语义

超预算返回稳定错误类型 `ContextLengthExceeded`，错误正文明确包含：

- 预计输入 Token。
- 当前模型上下文上限。
- 输出预留。
- 安全余量。
- “不会自动切换模型”的说明。

这样前端和日志不需要解析各家 Provider 不同的错误字符串。

## 6. 修复三：深度笔记分块知识账本

### 6.1 删除静默字符截断

深度笔记不再截断 300,000 字符。所有符合条件的已完成消息都会进入来源集合。助手的原始 reasoning 仍保留在 Chat 界面和会话数据中，但默认不作为深度笔记来源，防止模型内部推理污染事实笔记。

每条消息在转写中保留稳定锚点：

```html
<!-- message-id: message-uuid -->
```

### 6.2 深度笔记专用预算

`DeepNoteContextBudget` 保存：

- 模型上下文窗口。
- 来源预计输入 Token。
- Planner 输出预留。
- Prompt 开销预留。
- 安全余量。
- 可用输入预算。
- 直接规划上限。
- 分块目标。
- 总分块和已处理分块。
- 总消息和已处理消息。
- 是否完整覆盖。
- 未处理消息 ID。

默认值：

| 项目 | 默认值 |
| --- | ---: |
| 直接 Planner 输入上限 | 24K Token |
| 已知上下文的来源分块目标 | 最高 16K Token |
| 未知上下文的来源分块目标 | 8K Token |
| 单次任务最多来源分块 | 96 |

超过 96 个分块时任务会明确失败并要求缩小范围，不会截掉尾部继续生成。

### 6.3 分块算法

分块按以下层级执行：

1. 优先保持完整消息。
2. 一条消息过长时，优先按空行分隔的段落拆分。
3. 单个段落仍然过长时，按 Unicode 字符线性拆分。
4. 每个子块都保留所属消息 ID 元数据。
5. 合并子块时把分隔符本身计入 Token 预算。

算法不会使用“对当前字符串每追加一个字符就重新扫描全部正文”的方式，避免超长文本出现平方级前端或后端开销。

### 6.4 分块提取内容

每个来源分块调用 `CHUNK_ANALYST_SYSTEM_PROMPT`，提取结构化 `ChunkDigest`：

- `summary`。
- `canonicalTerms`。
- `verifiedFacts`。
- `coveredTopics`。
- `openQuestions`。
- `conflicts`。
- `globalConstraints`。
- `sourceMessageIds`。

空摘要不会被标记为已覆盖，而是先触发一次严格 JSON 修复；修复后仍为空则终止该分块，防止“调用成功但没有提取任何内容”被计入 100% 覆盖。

模型返回的来源消息 ID 会与当前分块真实 ID 求交集。模型虚构的 ID 不会进入知识账本。

### 6.5 增量持久化和恢复

每个分块成功后立即执行：

1. 合并到 `DeepNoteLedger`。
2. 更新已处理分块数和消息覆盖数。
3. 保存 `DeepNoteRuntimeState`。
4. 写入 `contextChunkCompleted` 事件。

来源原文分块写入现有 SQLite 表 `note_pipeline_source_chunks`。WebView 的详情接口只返回分块数量，不返回全部来源正文，避免大文本常驻前端内存。

任务中断后，若分块数量、分块目标和已保存运行状态一致，可从下一个未完成分块继续。来源变化或预算变化时会重建账本，避免把旧分块结果错误复用到新输入。

### 6.6 覆盖率门禁

只有同时满足以下条件才把 `coverageComplete` 设为 `true`：

```text
processed_chunk_count == chunk_count
且
去重后的 processed_message_ids == total_message_count
```

不完整时计算 `omittedMessageIds` 并阻止继续生成完整笔记。这里的覆盖含义是“每条来源消息都经过了分块提取”，不是“模型一定理解了所有语义”；后者仍需依赖章节校验和用户审阅。

### 6.7 按章加载来源

提纲中的每个章节包含 `sourceMessageIds`。章节生成时优先只加载这些 ID 对应的原文，而不是为每一章重复发送完整会话。

```text
章节来源原文在预算内
  -> 加载真实原文和消息锚点

章节来源原文超预算
  -> 加载带来源消息 ID 的分块账本摘要

既无原文也无可追溯摘要
  -> 阻止该章节生成并返回计划修复提示
```

这降低了每章请求体、重复 Token 和内存峰值，同时保留来源追踪能力。

## 7. 修复四：普通 Chat 超长上下文压缩

### 7.1 新的压缩触发公式

前端可用输入预算为：

```text
input_budget = context_window_tokens
             - max_output_tokens
             - max(4096, context_window_tokens * 8%)
```

预计输入超过 `input_budget` 时才触发自动压缩，不再使用“整个上下文窗口的 90%”这一粗略规则。

Rust 后端使用略保守的 `context / 12` 安全余量作为最终门禁，所以接近边界时以后端判断为准。

### 7.2 分块层级压缩

压缩候选仍保留最近 4 条消息不动，较早历史按最高 16K Token 的目标拆成多个批次。每个批次执行：

```text
已有摘要 + 当前历史分块
  -> 模型生成新的合并摘要
  -> 新摘要进入下一批
```

这样无需一次把所有待压缩历史发给模型。单条超长消息也会按段落和字符继续拆分，不会因为消息数组只有一个元素而失去分块能力。

压缩输入还额外预留 6,144 Token，用于已有摘要、System Prompt 和协议开销。如果模型可用输入连这部分和最小工作分块都容纳不了，前端会明确要求降低最大输出 Token 或修正模型上下文配置，不发送已知超预算请求。

### 7.3 压缩保留项

压缩 Prompt 明确要求保留：

- 已确认事实。
- 用户偏好和约束。
- 关键结论。
- 文献名称和页码。
- 代码或文件名称。
- 待办事项。
- 尚未解决的问题。
- 用户手动指定的压缩重点。

压缩结果为空时立即报错，不把空字符串保存为有效上下文摘要。

### 7.4 Context Usage 界面

上下文圆环现在以“可用输入预算”为分母，而不是以整个 Context Window 为分母。展开详情会分别显示：

- System Prompt。
- 对话消息。
- 附件。
- 已激活 Skills。
- 工具定义。
- 工具结果。
- 最大输出预留。
- 安全余量。

这让用户看到的是“还能输入多少”，而不是容易误导的“总窗口还剩多少”。

## 8. 深度笔记进度界面

深度笔记工作区新增真实任务状态区域，显示：

- 当前 Phase。
- 最近更新时间。
- 当前状态正文。
- 请求序号与最大请求次数。
- 已重试次数。
- 当前调用已等待时间。
- 下一次重试的退避时间。
- 最近一次错误。
- 总章节、已完成、生成中、失败和剩余数量。
- 每章的尝试次数、修订次数和错误。
- 语义调用预算。
- 来源消息覆盖率和来源分块进度。
- 任务错误、部分草稿和检查警告。

来源分块的 `current/total` 不再被误当成章节生成进度。章节进度只在 `drafting`、`validating` 和 `replanning` 等章节阶段参与任务进度计算。

任务完成、失败或取消后，详情仍保留在深度笔记工作区，用户可以检查过程和部分结果，不再只能依赖短暂 Toast。

## 9. 错误分类与行为矩阵

| 情况 | 是否重试 | 是否 JSON 修复 | 是否分块回退 | 是否换模型 |
| --- | --- | --- | --- | --- |
| 限流或临时连接失败 | 按设置，最多 5 次 | 否 | 直接 Planner 时是 | 否 |
| 单次请求超时 | 按设置；直接 Planner 首次不重复大请求 | 否 | 直接 Planner 时是 | 否 |
| Provider 临时错误 | 按错误分类 | 否 | 直接 Planner 时是 | 否 |
| 上下文过长 | 否或由 Provider 分类决定 | 否 | 直接 Planner 时是 | 否 |
| HTTP 成功但 JSON 无效 | 不按网络错误重试 | 是 | 否 | 否 |
| 分块摘要为空 | 否 | 是 | 已经处于分块流程 | 否 |
| 认证或权限失败 | 否 | 否 | 否 | 否 |
| 用户取消 | 否 | 否 | 否 | 否 |

## 10. 内存与性能约束

本次修复专门避免把上下文治理本身变成新的内存问题：

- 来源正文持久化在 SQLite，详情接口不把全部分块正文发送给 WebView。
- 普通 Chat 和深度笔记都以分块串行处理为主，不同时保留多份完整模型请求。
- 前端超长字符串分块使用线性 Token Unit 计数。
- 后端按字符线性估算 Token，不加载常驻 Tokenizer 模型。
- 章节只加载相关消息，减少重复构造完整会话字符串。
- 助手 reasoning 不复制到深度笔记 Planner 输入。
- 每个成功分块立即持久化，恢复时无需重放已经完成的全部模型调用。

## 13. 验收场景

### 13.1 深度笔记等待与取消

1. 使用一个响应较慢的模型启动深度笔记。
2. 确认界面显示请求序号、已等待秒数和重试上限。
3. 在请求等待中点击取消。
4. 确认状态很快变为取消，而不是继续等待到 240 或 360 秒超时。
5. 若已经完成章节，确认笔记库存在草稿且未完成章节未被标记成功。

### 13.2 Provider 临时失败

1. 使用会返回 429 或临时 5xx 的测试网关。
2. 确认界面显示最近错误和下一次重试等待。
3. 确认最多执行设置快照中的 5 次重试。
4. 运行中修改重试设置，确认当前任务仍使用启动时快照。

### 13.3 超长 Planner

1. 构造超过 24K Token 的多轮会话。
2. 启动深度笔记。
3. 确认进入来源分块提取，并逐步增加已处理分块和消息数。
4. 中途退出应用后重新打开。
5. 确认从未完成分块继续，而不是从第一个分块重新开始。

### 13.4 覆盖门禁

1. 构造接近 96 个分块的合成会话。
2. 让某个分块返回空摘要或持续失败。
3. 确认覆盖状态不是“完整”。
4. 确认任务不会继续生成一个伪装成完整结果的笔记。

### 13.5 普通 Chat 长上下文

1. 构造超过模型可用输入预算的历史消息。
2. 确认压缩按多个批次执行。
3. 确认最近 4 条消息未被压缩。
4. 确认摘要保留用户约束、引用页码、文件名和未完成事项。
5. 构造一条本身超过批次目标的消息，确认仍可继续拆分且 WebView 不出现长时间冻结。

## 14. 已知边界与后续方向

1. 本地 Token 估算不是供应商官方 Tokenizer。当前通过安全余量和后端硬门禁控制误差，未来可针对主要模型增加按需加载的精确 Tokenizer，但不能成为常驻内存负担。
2. 未知模型没有可靠的上下文窗口，普通 Chat 只能依赖保守行为和 Provider 最终错误。设置页应鼓励用户为自定义模型填写真实窗口。
3. 分块提取属于有损语义压缩。“完整覆盖”只证明每条消息进入过提取流程，不证明模型没有遗漏细节，因此仍需章节来源、验证报告和用户确认。
4. 96 个分块是单次任务的工程上限，不是模型能力声明。更大资料集应在未来使用可选择范围、检索索引或多级 Map-Reduce 账本，而不是继续提高单次常驻数据量。
5. 当前图片 Token 使用 1,200/张的本地估算。不同 Provider 的视觉计费方式不同，后续可在保留安全余量的前提下按图片尺寸和协议细化。
6. Release 环境仍需使用合成数据和真实用户数据分别采集 idle、普通 Chat、超长 Chat、单 PDF 与深度笔记的内存峰值，确认分块持久化没有引入新的 WebView 常驻对象。

## 15. 最终结果

修复后的核心变化可以概括为：

```text
过去：一次大请求 + 粗粒度文案 + 阶段边界取消 + 可能截断

现在：
  明确预算
  -> 直接规划或无遗漏分块
  -> 增量知识账本与持久化
  -> 按章加载相关来源
  -> 真实请求/重试/覆盖进度
  -> 可穿透网络等待的取消
  -> Rust 最终上下文硬门禁
```

这次修复把“看起来卡住”的问题拆解成可观测、可取消、可恢复、可验证的运行流程，同时为普通 Chat 和深度笔记建立了统一的上下文治理基础。

## 16. 本轮补充：深度笔记工作流和可观测性重构

### 16.1 为什么必须补充这一轮记录

前面的修复已经让运行层具备了取消、暂停、恢复、分块、重试和上下文预算能力，但界面仍然把多个不同层次的事实并列显示：

- 上下文覆盖进度：表示输入消息是否已经进入规划输入。
- 知识结构分析：表示规划模型是否已经生成结构化提纲。
- 语义调用预算：表示已经消耗了多少次模型调用额度。
- 章节进度：只有用户确认提纲后才会开始有意义。

这些指标的生命周期不同，却曾经同时出现在同一个进度区域中。于是用户看到“上下文已经 24/24，但仍然分析知识结构”，很容易判断为重复处理、死循环或状态竞争。

本轮的核心原则是：

```text
一个主状态：当前运行阶段
一条主流程：任务从输入到笔记的顺序
一份事件日志：每个真实动作的开始、完成、失败和等待
多个辅助指标：只解释当前主状态，不与主状态竞争
```

### 16.2 当前真实执行顺序

深度笔记实际采用的是 Plan-and-Execute 管线。它不是“所有工作同时发生”，也不是额外启动一个独立规划器模型，而是由运行层按阶段组织模型请求和本地持久化。

```text
阶段 1：输入与能力预检
  -> 冻结消息、附件、模型、权限和能力快照
  -> 检查文本、Tool、视觉和结构化输出能力
  -> 持久化 preflightCompleted

阶段 2：准备规划输入
  -> 估算完整会话的 Token 规模
  -> 计算 Planner 输出预留、Prompt 开销和安全余量
  -> 输入未超直接规划上限：建立直接规划输入
  -> 输入超出上限：拆分来源分块，逐块建立知识账本
  -> 每个分块完成后保存检查点
  -> 全部消息覆盖后持久化 contextCoverageCompleted

阶段 3：生成知识结构与提纲
  -> 直接规划模式：调用 Planner 生成结构化提纲
  -> 分块模式：根据知识账本调用 Planner 生成结构化提纲
  -> 等待模型响应时处于 analyzing
  -> 提纲成功解析后持久化 outlineReady

阶段 4：确认语义计划
  -> 运行层进入 awaitingOutline
  -> 用户查看章节、目标、读者和范围
  -> 用户可以删减章节或提出重新规划要求
  -> 用户确认后持久化 planConfirmed

阶段 5：生成并验证章节
  -> 编译章节执行计划和节点依赖
  -> 按已确认章节计划逐章生成
  -> 对每章进行结构、证据和成功标准验证
  -> 验证不通过时进入修订，受章节修订上限约束
  -> 每章完成后保存 sectionCompleted

阶段 6：组装并保存笔记
  -> 合并已完成章节
  -> 生成来源与运行侧车数据
  -> 写入笔记库和来源表
  -> 持久化 runCompleted
```

需要特别区分“知识结构生成”和“上下文覆盖”：上下文覆盖是输入准备阶段的结果，知识结构生成是输入准备完成后的模型请求。前者完成后，后者仍然可能需要等待数十秒或数分钟；这不是同一个阶段的重复工作。

### 16.3 截图所示状态的准确解释

当界面显示以下组合时：

```text
上下文覆盖：24 / 24
当前阶段：分析知识结构
章节：0 / 0
```

真实含义是：

1. 24 条消息已经被纳入 Planner 的输入范围。
2. 当前正在等待 Planner 模型返回知识结构和提纲 JSON。
3. 因为提纲尚未生成和确认，所以章节数量尚未建立，`0 / 0` 是正确状态。
4. 运行预算中的“7 / 12”是已经消耗的语义调用次数，不代表 7 个章节，也不代表上下文处理进度。

如果当前模型请求还没有超过单次超时窗口，这属于正常等待；如果超过超时窗口，则会记录 `modelCallFailed`，并根据错误类型和任务重试策略进入下一次请求或失败终止。

### 16.4 请求级活动模型

本轮将原来只有 `kind`、尝试次数和开始时间的活动信息扩展为：

| 字段 | 含义 |
| --- | --- |
| `kind` | `modelCall` 或 `retryWait` |
| `callId` | 本次逻辑模型调用的唯一标识 |
| `operation` | 当前操作用途，例如 `deepNote` |
| `attempt` | 当前第几次请求 |
| `maxRetries` | 失败后最多允许的重试次数 |
| `startedAt` | 当前 Attempt 的开始时间 |
| `timeoutMs` | 当前 Attempt 的最大等待窗口 |
| `delayMs` | 重试等待的退避时间 |
| `lastError` | 最近一次可恢复错误 |

这里必须区分“逻辑调用”和“网络 Attempt”：一次章节生成调用可能包含第一次请求和若干次重试，它们共享同一 `callId`，但每一次 Attempt 都有独立的开始时间和超时窗口。

当前输出规模对应的请求窗口为：

| 请求规模 | 单次 Attempt 超时 |
| --- | ---: |
| Planner、来源分块和 JSON 修复（最大输出不超过 8K） | 240 秒 |
| 较大章节生成或修订（最大输出超过 8K） | 360 秒 |

界面不再只显示“等待模型响应”，而会同时显示：

- 当前是第几次请求和总请求次数。
- 已经等待或已经耗时多久。
- 距离本次 Attempt 超时还剩多久。
- 当前是正常请求还是退避重试等待。
- 最近一次失败原因。

### 16.5 持久化运行事件

运行层现在将关键事件写入 `note_pipeline_events`，而不是只通过一次性的 Tauri Channel 通知前端。这样即使 WebView 刷新、详情轮询延迟或应用重新打开，用户仍然可以读取已经发生的过程。

本轮新增或统一使用的事件包括：

| 事件 | 记录时机 |
| --- | --- |
| `phaseProgress` | 阶段进度消息更新 |
| `modelCallStarted` | Provider Attempt 开始 |
| `modelRetryScheduled` | 请求失败并进入退避等待 |
| `modelCallCompleted` | 收到模型成功响应，记录耗时和返回字符数 |
| `modelCallFailed` | 当前逻辑调用最终失败，记录错误类型和耗时 |
| `contextChunkCompleted` | 一个来源分块完成并保存 |
| `contextCoverageCompleted` | 所有规划输入消息完成覆盖 |
| `outlineReady` | 结构化提纲成功生成并保存 |
| `planConfirmed` | 用户确认章节计划 |
| `sectionCompleted` | 一个章节通过验证并保存检查点 |
| `sectionFailed` | 一个章节达到上限仍未通过验证 |
| `runPaused` | 用户请求暂停 |
| `runResumed` | 从检查点继续运行 |
| `runCompleted` | 笔记和运行侧车保存完成 |
| `runFailed` | 任务进入最终错误状态 |

事件 payload 中保留阶段、请求 ID、章节 ID、尝试次数、耗时、覆盖数量、错误信息等诊断字段。详情接口最多读取最近 500 条事件，避免无限增长的日志一次性进入 WebView。

### 16.6 卡顿定位规则

当前界面将“卡顿”拆成四类，不再把所有等待都叫作模型思考：

#### A. 模型请求进行中

有 `modelCallStarted` 活动，且当前时间没有超过 `timeoutMs`。这表示网络请求仍在超时窗口内，界面显示已等待时间和剩余超时时间。

#### B. 重试退避等待

活动类型为 `retryWait`。界面显示最近错误、当前重试序号和下一次请求前的等待时间。取消会同时中断退避计时和后续请求。

#### C. 本地阶段处理

没有活动模型请求，但最近有 `phaseProgress` 或检查点事件。可能正在进行分块整理、账本合并、计划编译、章节组装或 SQLite 写入。

#### D. 事件静默

超过 30 秒没有收到新的运行事件。界面显示“没有收到新事件”，并建议从运行记录最后一项开始检查。这不直接断言发生 Bug，因为本地数据库锁、Provider 通道、WebView 事件同步都可能造成暂时静默；但它会给出明确排查起点。

### 16.7 前端界面重构

旧界面采用“输入快照栏 + 主进度卡 + 任务进度、运行预算、上下文覆盖、执行图多个右侧指标”的布局。它的问题是：

- 左侧输入信息占用固定宽度，却没有帮助判断当前卡点。
- 中央区域在提纲生成前过于空旷。
- 右侧多个指标同级排列，无法表达阶段先后。
- “上下文覆盖”和“分析知识结构”看起来像并行任务。
- 章节 `0 / 0` 缺少“尚未开始”的解释。
- 进度 Toast、中央状态和右侧状态存在重复。

本轮调整为：

```text
顶部：当前阶段 + 暂停/继续/停止
中央：当前阶段说明 + 请求诊断 + 提纲/章节内容 + 可折叠运行记录
右侧：六阶段工作流 + 输入模型信息 + 规划输入覆盖 + 预算 + 章节状态
```

主要交互变化：

- 删除原先重复的中央空状态和底部重复进度浮层。
- 没有提纲时显示“章节执行尚未开始”，明确当前仍在规划阶段。
- 右侧用纵向步骤连接线表达阶段顺序。
- 工作流步骤使用 `pending`、`active`、`completed`、`paused`、`failed` 和 `stopped` 状态。
- 运行记录默认可见，用户可以折叠；完成后仍然可以展开查看。
- 增加“复制运行诊断”按钮，用于把当前阶段、Run ID、模型、预算、活动请求和最近事件复制出来。
- 规划输入覆盖区域增加解释文本：覆盖完成不等于提纲已经生成。
- 章节进度只在提纲确认后显示，不再用 `0 / 0` 制造未定义的进度感。

### 16.8 工作流状态推导规则

前端没有根据颜色或文案猜测状态，而是根据运行详情中的事实推导工作流：

| 事实 | 对应步骤 |
| --- | --- |
| 有输入快照和预检结果 | 输入与能力预检完成 |
| `coverageComplete=true` | 准备规划输入完成 |
| 有 `planVersion.plan` | 知识结构与提纲生成完成 |
| `confirmedAt` 存在 | 语义计划确认完成 |
| 阶段进入 `assembling` 或 `persisting` | 章节执行已完成，进入保存 |
| 阶段为 `done` | 组装和保存完成 |
| 阶段为 `paused` | 当前未完成步骤显示暂停 |
| 阶段为 `error` 或 `cancelled` | 当前未完成步骤显示失败或停止 |

这种推导方式的好处是：即使前端错过某一条即时 Channel 事件，只要重新读取运行详情，工作流仍能根据持久化状态恢复正确显示。

### 16.9 本轮新增测试

新增 `deepNoteDiagnostics.test.ts`，覆盖：

1. 上下文覆盖完成但提纲规划仍进行中的状态不会被误报为章节执行。
2. 有活动模型请求时显示第几次 Attempt、已经等待时间和剩余超时窗口。
3. 持久化的模型完成事件可以转换为用户可读的耗时和响应长度。

已有验证结果：

- `cargo check` 通过。

## 17. 当前完整运行流程示例

以截图中的 24 条消息为例，直接规划模式可能经历以下事件：

```text
preflightCompleted
phaseProgress: 上下文预检完成
contextCoverageCompleted: 24/24 条消息，mode=direct
modelCallStarted: operation=deepNote, attempt=1/1
  -> 页面显示：生成知识结构，等待模型响应
modelCallCompleted: durationMs=...
outlineReady: sectionCount=N
  -> 页面显示：等待计划确认
planConfirmed: version=1
phaseProgress: 正在扩写 1/N
modelCallStarted: 章节请求
modelCallCompleted: 章节响应
sectionCompleted: 第 1 章
  -> 重复直到所有章节完成
phaseProgress: 正在组装与检查笔记
phaseProgress: 正在保存笔记与来源
runCompleted
```

如果直接规划首次请求超时，则流程不是无限重试同一大请求，而是：

```text
modelCallStarted
modelCallFailed: Timeout
phaseProgress: 直接规划未成功，切换到分块知识账本
contextChunkCompleted: 1/5
contextChunkCompleted: 2/5
...
contextCoverageCompleted: 24/24
modelCallStarted: 基于知识账本生成提纲
```

如果在模型请求中点击暂停：

```text
runPaused
CancellationToken 中断当前请求
保存已经完成的分块、章节和预算
paused
```

继续时不会重做已经完成的分块或章节，而是从最后一个持久化检查点恢复。

## 18. 后续优化方向

本轮已经解决“看不到卡在哪里”的问题，但仍有可以继续提升的方向：

1. 为运行事件增加可选的本地诊断级别，让开发调试模式显示更详细的请求大小、估算 Token 和数据库写入耗时，正式版本保持简洁。
2. 将 `phaseProgress` 进一步规范为阶段开始、阶段完成两个事件，减少大量同类进度事件的解释成本。
3. 在模型响应成功后记录 Provider 返回的真实 usage，并与本地估算并列展示，帮助校准不同模型的 Token 估算误差。
4. 为每个章节显示来源消息 ID 和验证报告摘要，让章节失败时可以直接判断是来源不足、模型输出问题还是验证规则问题。
5. 对超过 30 秒无事件的情况增加“刷新运行详情”和“复制诊断”快捷动作，但不自动重启正在运行的模型请求。
6. 在 Release 版本中继续使用合成数据和真实会话分别验证：直接规划、分块规划、模型超时、重试退避、暂停恢复和应用重启恢复。

## 20. 本轮最终结论

深度笔记的运行状态现在可以用三个问题解释，而不再依赖一条模糊的“分析知识结构”文案：

1. **任务处于哪个阶段？** 由六阶段工作流回答。
2. **当前是否真的在调用模型？** 由请求活动、Attempt、超时窗口和 `callId` 回答。
3. **如果没有模型请求，最后完成了什么、下一步是什么？** 由持久化运行事件和工作流检查点回答。

因此，用户看到“上下文覆盖完成但仍在分析知识结构”时，可以明确知道：输入已经准备完毕，当前只是在等待提纲规划模型，不是上下文覆盖重复执行；如果超过超时或长时间没有事件，运行记录会提供具体排查位置。

## 21. 四阶段任务进度入口优化

深度笔记工作区已经能够解释单次运行的详细状态，但用户切换到 Chat、文献或设置页面后，仍然需要回到深度笔记页面才能确认任务是否推进。Chat Agent 的思考、技能和工具活动则只存在于对应消息内部，长对话中难以快速定位。为解决“后台任务存在，但缺少全局、稳定、可回到详情的入口”这一问题，本轮参考桌面开发工具的任务 Pane 结构，完成了四阶段任务进度优化。

这次优化没有增加新的任务执行引擎。Rust 深度笔记运行层、深度笔记详情、Chat 消息和流式消息 Store 仍然是唯一事实来源；新任务中心只把这些事实转换为适合全局展示的轻量投影。这样避免出现“详情页显示一个状态、全局任务入口又维护另一个状态”的双状态问题。

### 21.1 第一阶段：统一任务投影模型

新增 `TaskRunProjection`，用于统一描述 Chat Agent 和深度笔记两类任务。它不是持久化实体，也不负责调度，而是从已有运行事实即时计算出来的只读界面模型。

核心字段如下：

| 字段 | 作用 |
| --- | --- |
| `id` | 任务中心使用的稳定任务 ID，包含任务类型和来源 ID |
| `sourceId` | 原始 Chat 消息 ID 或深度笔记 Run ID，用于打开完整详情 |
| `kind` | 区分 `chatAgent` 和 `deepNote` |
| `status` | 统一后的运行、等待、暂停、完成、失败和停止状态 |
| `statusLabel` | 面向用户的状态文案，不要求用户只通过颜色判断状态 |
| `currentStepLabel` | 当前工作流步骤名称 |
| `activity` | 当前正在发生的真实活动或最近错误 |
| `startedAt`、`updatedAt`、`finishedAt` | 用于运行时长、排序和终态保留时间计算 |
| `completedCount`、`totalCount` | 用于进度计数和进度条 |
| `steps` | 可展开查看的阶段、思考、技能或工具步骤 |
| `metrics` | Tool、Skill 和 Token 等可用指标 |
| `needsAttention` | 是否等待审批、确认、恢复或错误处理 |
| `canPause`、`canResume`、`canStop` | 根据原始运行状态计算出的可用操作 |

统一任务状态映射为：

| 统一状态 | 深度笔记来源 | Chat Agent 来源 |
| --- | --- | --- |
| `running` | 可执行的 Pipeline 阶段 | Agent 工作流正在生成或调用 |
| `waiting` | 等待提纲确认或能力阻塞 | 等待 Tool 审批或用户处理 |
| `paused` | 运行已持久化为暂停 | Agent 工作流暂停 |
| `completed` | `done` | Agent 工作流完成 |
| `failed` | `error` | 失败或预算耗尽 |
| `stopped` | `cancelled` | 用户停止或 Tool 被拒绝后停止 |

深度笔记在任务中心仍采用详情页相同的六阶段语义：

```text
输入与能力预检
准备规划输入
生成知识结构与提纲
确认语义计划
生成并验证章节
组装并保存笔记
```

任务中心直接复用 `buildDeepNoteWorkflow`，因此不会为同一运行维护第二套阶段判断。上下文覆盖完成但提纲尚未返回时，前两步显示完成，第三步显示运行中，不会再让“上下文覆盖”和“生成知识结构”看起来像两个互相冲突的并行任务。

### 21.2 第二阶段：右上角紧凑任务入口与展开面板

新增全局 `TaskCenter`。只有存在真实任务投影时，右上角才显示入口；没有深度笔记运行，也没有真实 Agent 活动时，不占用界面空间。

收起状态提供以下信息：

- 当前最高优先级任务的状态图标。
- 当前步骤，或正在运行、最近保留的任务数量。
- 已完成步骤数和总步骤数。
- 已运行时间。

展开面板提供以下信息：

- 多任务切换列表。
- 任务标题、状态和已用时。
- 真实步骤进度和当前活动。
- Tool、Skill 和 Token 指标。
- 深度笔记六阶段计划。
- Chat reasoning、Skill 和 Tool 步骤。
- 可渐进展开的思考内容和 Tool 结果预览。
- 暂停、继续、停止和完整详情操作。

界面采用固定上限宽度和视口高度约束，小窗口下入口收缩为 40px 图标按钮。状态同时使用图标、文字和颜色表达；工作区身份色用于区分 Chat 与深度笔记，成功、警告和失败仍使用独立语义色。面板保持 5 至 7px 圆角、Lucide 图标、单层工具面板结构，没有加入卡片墙、玻璃效果或装饰渐变。

### 21.3 第三阶段：接入深度笔记、Chat 详情和终态折叠

深度笔记任务入口直接接入现有运行控制：

- 运行中的可中断阶段显示“暂停”。
- 暂停状态显示“继续”。
- 未进入终态的任务显示“停止”。
- “完整详情”切换到深度笔记工作区，继续使用已有诊断、日志、预算和章节视图。

Chat Agent 任务严格遵守真实活动原则。只有消息中存在以下任意事实时，才建立 Chat 任务投影：

- 模型返回了 reasoning。
- 运行层真实激活了 Skill。
- 运行层产生了 Tool Trace。

普通 Chat 文本生成不会为了占满任务面板而虚构“规划、执行、反思”等步骤。当前模型不支持 reasoning 或 Tool 时，任务中心也不会伪造对应活动。

Chat 的“完整详情”会切换回 Chat 工作区，并通过消息元素的稳定 `message-{id}` 锚点定位到对应消息。完整 reasoning、Skill 和 Tool 工作流仍由消息内部原有界面展示，任务中心只提供可扫描摘要和返回路径。

当所有活跃任务进入完成、失败或停止状态后，展开面板自动折叠，避免完成后的工作流长期遮挡内容。终态入口不会立即消失，而是在 15 分钟内保留，用户可以重新打开检查结果、失败位置或过程内容；保留时间到期后，投影自然消失，不需要额外清理持久化数据。

### 21.4 第四阶段：多个后台任务聚合展示

任务中心支持同时聚合深度笔记和 Chat Agent。当前界面允许两类运行事实同时存在，例如深度笔记在后台生成章节时，用户在 Chat 中执行带 reasoning 或 Tool 的任务。

多个任务按照“是否需要用户处理”和“运行紧迫性”排序：

```text
等待处理 -> 失败 -> 暂停 -> 运行中 -> 已停止 -> 已完成
```

同一状态下，最近更新的任务排在前面。这个顺序确保 Tool 审批、提纲确认、失败和暂停任务不会被持续输出的普通运行任务挤到后面。面板顶部显示活跃任务数量，列表显示每个任务的类型、标题、当前步骤和状态图标；选择任务只改变面板投影，不修改原始执行状态。

### 21.5 流式性能边界

Chat reasoning 可能以高频增量到达。若在 `App` 根组件订阅流式 Store，每次 reasoning 增量都可能让应用壳、侧栏、工作区 Provider 和大量派生数据重新渲染。本轮将 `useStreamingMessage` 订阅限制在 `TaskCenter` 内部，根组件只传入最后一条助手消息的稳定数据。

这样可以让任务入口及时更新 reasoning，同时把最高约 30 FPS 的流式重渲染限制在一个紧凑组件内。任务计时器只在存在活跃任务时每秒更新；全部任务进入终态后停止周期计时，仅为最近终态的到期时间设置一次定时器。该设计避免为了显示已用时而让整个应用永久每秒重渲染。

Chat 是否运行由目标助手消息的 `pending`、`streaming` 状态和对应流式 Store 条目决定，不直接使用全局 `requestInFlight`。因此执行上下文压缩等其他请求时，不会把一条已经完成的历史 Agent 消息错误投影为“运行中”。

### 21.6 自动折叠与状态恢复规则

任务中心记录上一轮仍处于非终态的任务 ID 集合。当这个集合从非空变为空时，面板自动关闭。自动关闭只改变面板的本地展开状态，不删除任务、日志、消息或深度笔记检查点。

当前选择的任务消失时，组件自动选择排序后的第一项；任务列表为空时，同时清空选择并关闭入口。用户按 `Escape` 或点击面板外部也可以关闭。切换页面不会中断后台运行，因为任务控制仍由原始 Chat Runtime 和深度笔记 Runtime 负责。

### 21.7 测试覆盖

新增任务投影测试覆盖以下关键边界：

1. 普通 Chat 文本不会产生虚构任务。
2. 真实 reasoning 会产生可查看内容的 Chat Agent 任务。
3. 等待审批的 Tool 会映射为 `waiting` 和 `needsAttention=true`。
4. 深度笔记上下文覆盖完成后，任务准确停留在“生成知识结构与提纲”。

## 22. 四阶段优化后的完整使用流程

深度笔记和 Chat Agent 同时存在时，用户看到的流程为：

```text
运行层产生真实任务状态
  -> 投影层统一状态和步骤
  -> 右上角入口显示最高优先级任务
  -> 展开后可切换多个任务
  -> 需要时暂停、继续或停止深度笔记
  -> 点击完整详情回到深度笔记诊断页或具体 Chat 消息
  -> 所有任务结束后面板自动折叠
  -> 终态入口保留 15 分钟供复查
```

这套结构将“随时知道后台任务进行到哪里”和“进入完整页面诊断具体卡点”分成两个层次：右上角入口负责全局可见性和快速控制，深度笔记页与 Chat 消息工作流负责完整事实和诊断。两层都读取同一运行事实，因此不会因为新增全局进度入口而引入第二套执行状态。
