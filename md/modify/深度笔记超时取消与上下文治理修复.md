# 深度笔记超时、取消与上下文治理修复

## 1. 文档目的

本文记录一次围绕深度笔记和超长对话的系统性修复。修复不是单纯更换加载文案，而是同时调整模型请求生命周期、Token 预算、长会话分析管线、普通 Chat 压缩策略和进度可观测性。

本次处理的四个核心问题是：

1. 深度笔记长时间停在“建立输入快照与语义计划”，用户无法判断是在工作、重试还是已经失效。
2. 普通 Chat 和深度笔记都可能把超过模型上下文窗口的请求直接发给供应商。
3. 深度笔记曾以单次大请求分析完整会话，超长会话只能截断、失败或反复发送相同的大请求。
4. 普通 Chat 的旧压缩触发条件和单次压缩方式无法稳定处理超长消息及超长会话。

修复目标遵循以下边界：

- 不自动替换用户选择的模型或 Provider。
- 不静默截断来源，不把部分覆盖伪装成完整覆盖。
- Skill、Tool、重试、进度和来源覆盖只展示真实运行状态。
- 用户取消后要中断当前网络等待，而不是只在章节结束后检查一个布尔值。
- 在控制内存和请求体体积的同时，不能以明显卡顿或不可恢复为代价。

## 2. 问题现象与根因

### 2.1 “建立输入快照与语义计划”长时间不动

旧界面只知道管线处于 `analyzing` 阶段，不知道当前模型请求的内部状态。因此下面这些完全不同的情况会显示成同一句话：

- 正在读取输入快照。
- 正在等待第一次模型响应。
- 请求已经超时，正在等待退避重试。
- Provider 连续失败，正在重复发送相同的大请求。
- 模型返回了无法解析的 JSON，正在进行结构修复。
- 用户已经点击取消，但当前 HTTP 请求尚未结束。

根因是前端只有粗粒度 Phase，没有请求序号、重试次数、开始时间、退避时间和最近错误；后端非流式调用也没有接收外部取消令牌和单次调用超时。

### 2.2 相同大请求可能被重复发送

深度笔记 Planner 原来直接把完整会话发送给模型。若请求因为网络、Provider 或上下文长度失败，通用重试层会再次发送完全相同的 Payload。对于已经过大的请求，这种重试没有改变失败条件，只会增加等待时间、费用风险和用户的不确定感。

此外，网络失败与 JSON 解析失败原本缺少清晰边界。正确语义应当是：

- HTTP 请求失败：没有可供解析的响应，不能进入 JSON 修复。
- HTTP 请求成功但 JSON 无效：可以追加严格 JSON 约束，再进行一次结构修复调用。
- 大请求超时、连接失败、Provider 失败或上下文过长：直接缩小请求，切换到分块知识账本流程。

### 2.3 取消不能穿透到正在等待的网络请求

旧管线主要在章节或阶段边界检查取消状态。若模型请求正在等待 5 分钟，点击取消后仍可能继续等待到请求返回或超时。

本质问题是取消状态没有贯穿以下完整调用链：

```text
界面取消按钮
  -> Tauri 取消命令
  -> 活动深度笔记运行注册表
  -> CancellationToken
  -> 非流式模型调用
  -> 当前 HTTP Future / 超时 Future / 重试退避等待
```

### 2.4 上下文控制只看“总窗口比例”

模型上下文窗口并不全部属于输入。至少需要同时容纳：

- System Prompt。
- 对话消息。
- Tool Schema。
- Tool Call 和 Tool Result。
- 图片输入的视觉 Token 估算。
- 本轮最大输出。
- Tokenizer 误差、Provider 包装字段和协议差异所需的安全余量。

旧版前端以“达到上下文窗口的 90%”作为自动压缩触发条件。这意味着输入已经占用 90% 后，仍未明确给输出和安全余量留出空间。即便前端判断可以发送，Provider 仍可能返回 `context_length_exceeded`。

### 2.5 深度笔记的字符截断会破坏完整性

旧流程存在 300,000 字符上限。超过部分被截掉后，模型和用户都无法知道哪些消息没有进入分析。这样产生的笔记可能看起来完整，实际只覆盖会话前半部分。

字符数也不是可靠的上下文单位。英文、中文、代码、JSON 和不同模型 Tokenizer 的比例不同，因此必须把字符上限改成显式的 Token 预算和覆盖率。

### 2.6 单次压缩无法处理超长单消息

普通 Chat 原来的压缩请求会一次发送所有候选历史。若单条用户消息本身已经很长，简单地按消息数组分组仍无效，因为这一条消息就可能超过模型输入预算。

同时，逐字符反复估算整个字符串会形成近似平方级开销。超长文本可能让 WebView 主线程出现明显卡顿。因此分段算法必须是线性扫描，并按消息、段落、字符三级退化。

## 3. 总体修复架构

修复后形成两层保护：

```text
前端预算与预处理
  ├─ 普通 Chat：估算可用输入预算，必要时分块压缩
  ├─ 深度笔记：展示预算、分块和覆盖进度
  └─ Context Usage：按可用输入而不是总窗口显示
                 |
                 v
Rust 运行层硬校验
  ├─ 最终请求成形后重新估算
  ├─ 包含 System、消息、Tool Schema、工具结果和图片估算
  ├─ 预留最大输出与安全余量
  └─ 超预算返回 ContextLengthExceeded，不切换模型
```

前端负责尽早发现和处理，Rust 后端负责最终兜底。不能只依赖前端，因为请求在 Rust 层还可能注入 Tool、Skill、Memory 和 Agent Runtime Prompt；也不能只依赖后端，因为等到发送前才报错会让长对话缺少自动压缩体验。

## 4. 修复一：深度笔记请求生命周期

### 4.1 可配置的执行上下文

非流式模型调用新增 `CompleteExecution`，允许调用方传入：

- `CancellationToken`：控制当前请求和后续工具执行的真实取消。
- `max_retries`：使用任务启动时保存的重试快照，不受运行中设置变化影响。
- `attempt_timeout`：限制每次 HTTP 模型调用的等待时间。
- `on_progress`：接收请求开始和重试退避事件。

普通 Chat 的原有 `complete` 接口仍然保留，由它创建默认执行上下文；深度笔记使用 `complete_with_execution` 注入自己的取消、超时和进度规则。

### 4.2 超时规则

当前规则按预计输出规模区分：

| 调用 | 单次超时 |
| --- | ---: |
| Planner、来源分块提取、JSON 修复 | 240 秒 |
| 较大章节生成或修订 | 360 秒 |

超时只终止本次 Attempt。是否重试由错误分类和任务快照中的重试设置共同决定。

### 4.3 重试规则

用户当前默认自动重试为 5 次。这里的“5 次”指第一次请求失败后最多再尝试 5 次，因此界面显示的最大请求次数是 6。

重试只处理可恢复错误，例如限流、连接失败、超时和部分 Provider 临时错误。认证失败、无效配置、内容过滤、用户取消等错误不会进入盲目重试。

重试等待使用同一个取消令牌：

```text
请求失败
  -> 计算 Retry-After 或指数退避
  -> 同时等待“取消令牌”与“退避计时器”
  -> 用户取消：立即结束
  -> 计时器先结束：进入下一次 Attempt
```

### 4.4 Planner 的特殊规则

Planner 第一次直接分析完整会话时，网络重试次数强制为 0。原因是这个请求本身可能太大，重复发送相同 Payload 无法解决根因。

第一次直接 Planner 的结果分为三类：

1. 成功且 JSON 合法：直接进入提纲确认。
2. 成功但 JSON 非法：追加严格 JSON 约束，进行结构修复。
3. 超时、连接、Provider 或上下文长度错误：清空直接规划的临时覆盖状态，切换到小分块知识账本。

用户取消不属于第三类，不会错误地触发分块或 JSON 修复。

### 4.5 真实取消

当前模型调用使用 `tokio::select!` 同时等待：

- Provider 请求完成。
- `CancellationToken` 被取消。

取消令牌也传入 Tool 执行和重试退避等待。深度笔记停止后：

- 尚未产生提纲时，任务进入 `cancelled`。
- 已完成部分章节时，已完成内容保留并可组装为草稿。
- 未完成章节不会被标记为成功。
- 当前网络等待不再继续占用完整超时时间。

## 5. 修复二：统一 Token 上下文预算

### 5.1 后端硬预算公式

已知模型上下文窗口时，Rust 运行层使用：

```text
required_tokens = estimated_input_tokens
                + output_reserve_tokens
                + safety_margin_tokens

safety_margin_tokens = max(4096, context_window_tokens / 12)
```

只有 `required_tokens <= context_window_tokens` 才允许发送。

`estimated_input_tokens` 包含：

- System Prompt 文本。
- 每条消息正文和消息结构开销。
- Tool Call 参数。
- Tool Result 正文。
- 最终披露的 Tool 名称、描述和 JSON Schema。
- 每张图片 1,200 Token 的保守本地估算。

校验位置位于请求最终成形之后，因此 Agent Runtime Prompt、Skill 内容、Memory 和 Tool Schema 不会绕过预算检查。

### 5.2 估算策略

为避免引入常驻 Tokenizer 和额外内存，当前采用轻量估算：

```text
ASCII Token ~= ceil(ASCII 字符数 / 4)
非 ASCII Token ~= 非 ASCII 字符数
```

它不是供应商官方 Tokenizer 的精确结果，因此仍保留至少 4,096 Token 的安全余量。供应商真实用量可继续作为前端上下文显示的锚点，但发送前不能只依赖历史实报值。

### 5.3 模型上下文来源

上下文窗口按以下优先级解析：

1. 用户在模型配置中显式填写的 `contextWindowTokens`。
2. Mnemora 内置模型数据库的上下文窗口。
3. 两者都没有时为未知。

未知不会伪造一个“模型真实支持值”，也不会自动切换模型。普通 Chat 无法执行精确后端硬校验；深度笔记则采用 8K 输入预算进行保守分块，并在 Provider 拒绝时展示真实错误。

### 5.4 超预算错误语义

超预算返回稳定错误类型 `ContextLengthExceeded`，错误正文明确包含：

- 预计输入 Token。
- 当前模型上下文上限。
- 输出预留。
- 安全余量。
- “不会自动切换模型”的说明。

这样前端和日志不需要解析各家 Provider 不同的错误字符串。

## 6. 修复三：深度笔记分块知识账本

### 6.1 删除静默字符截断

深度笔记不再截断 300,000 字符。所有符合条件的已完成消息都会进入来源集合。助手的原始 reasoning 仍保留在 Chat 界面和会话数据中，但默认不作为深度笔记来源，防止模型内部推理污染事实笔记。

每条消息在转写中保留稳定锚点：

```html
<!-- message-id: message-uuid -->
```

### 6.2 深度笔记专用预算

`DeepNoteContextBudget` 保存：

- 模型上下文窗口。
- 来源预计输入 Token。
- Planner 输出预留。
- Prompt 开销预留。
- 安全余量。
- 可用输入预算。
- 直接规划上限。
- 分块目标。
- 总分块和已处理分块。
- 总消息和已处理消息。
- 是否完整覆盖。
- 未处理消息 ID。

默认值：

| 项目 | 默认值 |
| --- | ---: |
| 直接 Planner 输入上限 | 24K Token |
| 已知上下文的来源分块目标 | 最高 16K Token |
| 未知上下文的来源分块目标 | 8K Token |
| 单次任务最多来源分块 | 96 |

超过 96 个分块时任务会明确失败并要求缩小范围，不会截掉尾部继续生成。

### 6.3 分块算法

分块按以下层级执行：

1. 优先保持完整消息。
2. 一条消息过长时，优先按空行分隔的段落拆分。
3. 单个段落仍然过长时，按 Unicode 字符线性拆分。
4. 每个子块都保留所属消息 ID 元数据。
5. 合并子块时把分隔符本身计入 Token 预算。

算法不会使用“对当前字符串每追加一个字符就重新扫描全部正文”的方式，避免超长文本出现平方级前端或后端开销。

### 6.4 分块提取内容

每个来源分块调用 `CHUNK_ANALYST_SYSTEM_PROMPT`，提取结构化 `ChunkDigest`：

- `summary`。
- `canonicalTerms`。
- `verifiedFacts`。
- `coveredTopics`。
- `openQuestions`。
- `conflicts`。
- `globalConstraints`。
- `sourceMessageIds`。

空摘要不会被标记为已覆盖，而是先触发一次严格 JSON 修复；修复后仍为空则终止该分块，防止“调用成功但没有提取任何内容”被计入 100% 覆盖。

模型返回的来源消息 ID 会与当前分块真实 ID 求交集。模型虚构的 ID 不会进入知识账本。

### 6.5 增量持久化和恢复

每个分块成功后立即执行：

1. 合并到 `DeepNoteLedger`。
2. 更新已处理分块数和消息覆盖数。
3. 保存 `DeepNoteRuntimeState`。
4. 写入 `contextChunkCompleted` 事件。

来源原文分块写入现有 SQLite 表 `note_pipeline_source_chunks`。WebView 的详情接口只返回分块数量，不返回全部来源正文，避免大文本常驻前端内存。

任务中断后，若分块数量、分块目标和已保存运行状态一致，可从下一个未完成分块继续。来源变化或预算变化时会重建账本，避免把旧分块结果错误复用到新输入。

### 6.6 覆盖率门禁

只有同时满足以下条件才把 `coverageComplete` 设为 `true`：

```text
processed_chunk_count == chunk_count
且
去重后的 processed_message_ids == total_message_count
```

不完整时计算 `omittedMessageIds` 并阻止继续生成完整笔记。这里的覆盖含义是“每条来源消息都经过了分块提取”，不是“模型一定理解了所有语义”；后者仍需依赖章节校验和用户审阅。

### 6.7 按章加载来源

提纲中的每个章节包含 `sourceMessageIds`。章节生成时优先只加载这些 ID 对应的原文，而不是为每一章重复发送完整会话。

```text
章节来源原文在预算内
  -> 加载真实原文和消息锚点

章节来源原文超预算
  -> 加载带来源消息 ID 的分块账本摘要

既无原文也无可追溯摘要
  -> 阻止该章节生成并返回计划修复提示
```

这降低了每章请求体、重复 Token 和内存峰值，同时保留来源追踪能力。

## 7. 修复四：普通 Chat 超长上下文压缩

### 7.1 新的压缩触发公式

前端可用输入预算为：

```text
input_budget = context_window_tokens
             - max_output_tokens
             - max(4096, context_window_tokens * 8%)
```

预计输入超过 `input_budget` 时才触发自动压缩，不再使用“整个上下文窗口的 90%”这一粗略规则。

Rust 后端使用略保守的 `context / 12` 安全余量作为最终门禁，所以接近边界时以后端判断为准。

### 7.2 分块层级压缩

压缩候选仍保留最近 4 条消息不动，较早历史按最高 16K Token 的目标拆成多个批次。每个批次执行：

```text
已有摘要 + 当前历史分块
  -> 模型生成新的合并摘要
  -> 新摘要进入下一批
```

这样无需一次把所有待压缩历史发给模型。单条超长消息也会按段落和字符继续拆分，不会因为消息数组只有一个元素而失去分块能力。

压缩输入还额外预留 6,144 Token，用于已有摘要、System Prompt 和协议开销。如果模型可用输入连这部分和最小工作分块都容纳不了，前端会明确要求降低最大输出 Token 或修正模型上下文配置，不发送已知超预算请求。

### 7.3 压缩保留项

压缩 Prompt 明确要求保留：

- 已确认事实。
- 用户偏好和约束。
- 关键结论。
- 文献名称和页码。
- 代码或文件名称。
- 待办事项。
- 尚未解决的问题。
- 用户手动指定的压缩重点。

压缩结果为空时立即报错，不把空字符串保存为有效上下文摘要。

### 7.4 Context Usage 界面

上下文圆环现在以“可用输入预算”为分母，而不是以整个 Context Window 为分母。展开详情会分别显示：

- System Prompt。
- 对话消息。
- 附件。
- 已激活 Skills。
- 工具定义。
- 工具结果。
- 最大输出预留。
- 安全余量。

这让用户看到的是“还能输入多少”，而不是容易误导的“总窗口还剩多少”。

## 8. 深度笔记进度界面

深度笔记工作区新增真实任务状态区域，显示：

- 当前 Phase。
- 最近更新时间。
- 当前状态正文。
- 请求序号与最大请求次数。
- 已重试次数。
- 当前调用已等待时间。
- 下一次重试的退避时间。
- 最近一次错误。
- 总章节、已完成、生成中、失败和剩余数量。
- 每章的尝试次数、修订次数和错误。
- 语义调用预算。
- 来源消息覆盖率和来源分块进度。
- 任务错误、部分草稿和检查警告。

来源分块的 `current/total` 不再被误当成章节生成进度。章节进度只在 `drafting`、`validating` 和 `replanning` 等章节阶段参与任务进度计算。

任务完成、失败或取消后，详情仍保留在深度笔记工作区，用户可以检查过程和部分结果，不再只能依赖短暂 Toast。

## 9. 错误分类与行为矩阵

| 情况 | 是否重试 | 是否 JSON 修复 | 是否分块回退 | 是否换模型 |
| --- | --- | --- | --- | --- |
| 限流或临时连接失败 | 按设置，最多 5 次 | 否 | 直接 Planner 时是 | 否 |
| 单次请求超时 | 按设置；直接 Planner 首次不重复大请求 | 否 | 直接 Planner 时是 | 否 |
| Provider 临时错误 | 按错误分类 | 否 | 直接 Planner 时是 | 否 |
| 上下文过长 | 否或由 Provider 分类决定 | 否 | 直接 Planner 时是 | 否 |
| HTTP 成功但 JSON 无效 | 不按网络错误重试 | 是 | 否 | 否 |
| 分块摘要为空 | 否 | 是 | 已经处于分块流程 | 否 |
| 认证或权限失败 | 否 | 否 | 否 | 否 |
| 用户取消 | 否 | 否 | 否 | 否 |

## 10. 内存与性能约束

本次修复专门避免把上下文治理本身变成新的内存问题：

- 来源正文持久化在 SQLite，详情接口不把全部分块正文发送给 WebView。
- 普通 Chat 和深度笔记都以分块串行处理为主，不同时保留多份完整模型请求。
- 前端超长字符串分块使用线性 Token Unit 计数。
- 后端按字符线性估算 Token，不加载常驻 Tokenizer 模型。
- 章节只加载相关消息，减少重复构造完整会话字符串。
- 助手 reasoning 不复制到深度笔记 Planner 输入。
- 每个成功分块立即持久化，恢复时无需重放已经完成的全部模型调用。

## 13. 验收场景

### 13.1 深度笔记等待与取消

1. 使用一个响应较慢的模型启动深度笔记。
2. 确认界面显示请求序号、已等待秒数和重试上限。
3. 在请求等待中点击取消。
4. 确认状态很快变为取消，而不是继续等待到 240 或 360 秒超时。
5. 若已经完成章节，确认笔记库存在草稿且未完成章节未被标记成功。

### 13.2 Provider 临时失败

1. 使用会返回 429 或临时 5xx 的测试网关。
2. 确认界面显示最近错误和下一次重试等待。
3. 确认最多执行设置快照中的 5 次重试。
4. 运行中修改重试设置，确认当前任务仍使用启动时快照。

### 13.3 超长 Planner

1. 构造超过 24K Token 的多轮会话。
2. 启动深度笔记。
3. 确认进入来源分块提取，并逐步增加已处理分块和消息数。
4. 中途退出应用后重新打开。
5. 确认从未完成分块继续，而不是从第一个分块重新开始。

### 13.4 覆盖门禁

1. 构造接近 96 个分块的合成会话。
2. 让某个分块返回空摘要或持续失败。
3. 确认覆盖状态不是“完整”。
4. 确认任务不会继续生成一个伪装成完整结果的笔记。

### 13.5 普通 Chat 长上下文

1. 构造超过模型可用输入预算的历史消息。
2. 确认压缩按多个批次执行。
3. 确认最近 4 条消息未被压缩。
4. 确认摘要保留用户约束、引用页码、文件名和未完成事项。
5. 构造一条本身超过批次目标的消息，确认仍可继续拆分且 WebView 不出现长时间冻结。

## 14. 已知边界与后续方向

1. 本地 Token 估算不是供应商官方 Tokenizer。当前通过安全余量和后端硬门禁控制误差，未来可针对主要模型增加按需加载的精确 Tokenizer，但不能成为常驻内存负担。
2. 未知模型没有可靠的上下文窗口，普通 Chat 只能依赖保守行为和 Provider 最终错误。设置页应鼓励用户为自定义模型填写真实窗口。
3. 分块提取属于有损语义压缩。“完整覆盖”只证明每条消息进入过提取流程，不证明模型没有遗漏细节，因此仍需章节来源、验证报告和用户确认。
4. 96 个分块是单次任务的工程上限，不是模型能力声明。更大资料集应在未来使用可选择范围、检索索引或多级 Map-Reduce 账本，而不是继续提高单次常驻数据量。
5. 当前图片 Token 使用 1,200/张的本地估算。不同 Provider 的视觉计费方式不同，后续可在保留安全余量的前提下按图片尺寸和协议细化。
6. Release 环境仍需使用合成数据和真实用户数据分别采集 idle、普通 Chat、超长 Chat、单 PDF 与深度笔记的内存峰值，确认分块持久化没有引入新的 WebView 常驻对象。

## 15. 最终结果

修复后的核心变化可以概括为：

```text
过去：一次大请求 + 粗粒度文案 + 阶段边界取消 + 可能截断

现在：
  明确预算
  -> 直接规划或无遗漏分块
  -> 增量知识账本与持久化
  -> 按章加载相关来源
  -> 真实请求/重试/覆盖进度
  -> 可穿透网络等待的取消
  -> Rust 最终上下文硬门禁
```

这次修复把“看起来卡住”的问题拆解成可观测、可取消、可恢复、可验证的运行流程，同时为普通 Chat 和深度笔记建立了统一的上下文治理基础。

## 16. 本轮补充：深度笔记工作流和可观测性重构

### 16.1 为什么必须补充这一轮记录

前面的修复已经让运行层具备了取消、暂停、恢复、分块、重试和上下文预算能力，但界面仍然把多个不同层次的事实并列显示：

- 上下文覆盖进度：表示输入消息是否已经进入规划输入。
- 知识结构分析：表示规划模型是否已经生成结构化提纲。
- 语义调用预算：表示已经消耗了多少次模型调用额度。
- 章节进度：只有用户确认提纲后才会开始有意义。

这些指标的生命周期不同，却曾经同时出现在同一个进度区域中。于是用户看到“上下文已经 24/24，但仍然分析知识结构”，很容易判断为重复处理、死循环或状态竞争。

本轮的核心原则是：

```text
一个主状态：当前运行阶段
一条主流程：任务从输入到笔记的顺序
一份事件日志：每个真实动作的开始、完成、失败和等待
多个辅助指标：只解释当前主状态，不与主状态竞争
```

### 16.2 当前真实执行顺序

深度笔记实际采用的是 Plan-and-Execute 管线。它不是“所有工作同时发生”，也不是额外启动一个独立规划器模型，而是由运行层按阶段组织模型请求和本地持久化。

```text
阶段 1：输入与能力预检
  -> 冻结消息、附件、模型、权限和能力快照
  -> 检查文本、Tool、视觉和结构化输出能力
  -> 持久化 preflightCompleted

阶段 2：准备规划输入
  -> 估算完整会话的 Token 规模
  -> 计算 Planner 输出预留、Prompt 开销和安全余量
  -> 输入未超直接规划上限：建立直接规划输入
  -> 输入超出上限：拆分来源分块，逐块建立知识账本
  -> 每个分块完成后保存检查点
  -> 全部消息覆盖后持久化 contextCoverageCompleted

阶段 3：生成知识结构与提纲
  -> 直接规划模式：调用 Planner 生成结构化提纲
  -> 分块模式：根据知识账本调用 Planner 生成结构化提纲
  -> 等待模型响应时处于 analyzing
  -> 提纲成功解析后持久化 outlineReady

阶段 4：确认语义计划
  -> 运行层进入 awaitingOutline
  -> 用户查看章节、目标、读者和范围
  -> 用户可以删减章节或提出重新规划要求
  -> 用户确认后持久化 planConfirmed

阶段 5：生成并验证章节
  -> 编译章节执行计划和节点依赖
  -> 按已确认章节计划逐章生成
  -> 对每章进行结构、证据和成功标准验证
  -> 验证不通过时进入修订，受章节修订上限约束
  -> 每章完成后保存 sectionCompleted

阶段 6：组装并保存笔记
  -> 合并已完成章节
  -> 生成来源与运行侧车数据
  -> 写入笔记库和来源表
  -> 持久化 runCompleted
```

需要特别区分“知识结构生成”和“上下文覆盖”：上下文覆盖是输入准备阶段的结果，知识结构生成是输入准备完成后的模型请求。前者完成后，后者仍然可能需要等待数十秒或数分钟；这不是同一个阶段的重复工作。

### 16.3 截图所示状态的准确解释

当界面显示以下组合时：

```text
上下文覆盖：24 / 24
当前阶段：分析知识结构
章节：0 / 0
```

真实含义是：

1. 24 条消息已经被纳入 Planner 的输入范围。
2. 当前正在等待 Planner 模型返回知识结构和提纲 JSON。
3. 因为提纲尚未生成和确认，所以章节数量尚未建立，`0 / 0` 是正确状态。
4. 运行预算中的“7 / 12”是已经消耗的语义调用次数，不代表 7 个章节，也不代表上下文处理进度。

如果当前模型请求还没有超过单次超时窗口，这属于正常等待；如果超过超时窗口，则会记录 `modelCallFailed`，并根据错误类型和任务重试策略进入下一次请求或失败终止。

### 16.4 请求级活动模型

本轮将原来只有 `kind`、尝试次数和开始时间的活动信息扩展为：

| 字段 | 含义 |
| --- | --- |
| `kind` | `modelCall` 或 `retryWait` |
| `callId` | 本次逻辑模型调用的唯一标识 |
| `operation` | 当前操作用途，例如 `deepNote` |
| `attempt` | 当前第几次请求 |
| `maxRetries` | 失败后最多允许的重试次数 |
| `startedAt` | 当前 Attempt 的开始时间 |
| `timeoutMs` | 当前 Attempt 的最大等待窗口 |
| `delayMs` | 重试等待的退避时间 |
| `lastError` | 最近一次可恢复错误 |

这里必须区分“逻辑调用”和“网络 Attempt”：一次章节生成调用可能包含第一次请求和若干次重试，它们共享同一 `callId`，但每一次 Attempt 都有独立的开始时间和超时窗口。

当前输出规模对应的请求窗口为：

| 请求规模 | 单次 Attempt 超时 |
| --- | ---: |
| Planner、来源分块和 JSON 修复（最大输出不超过 8K） | 240 秒 |
| 较大章节生成或修订（最大输出超过 8K） | 360 秒 |

界面不再只显示“等待模型响应”，而会同时显示：

- 当前是第几次请求和总请求次数。
- 已经等待或已经耗时多久。
- 距离本次 Attempt 超时还剩多久。
- 当前是正常请求还是退避重试等待。
- 最近一次失败原因。

### 16.5 持久化运行事件

运行层现在将关键事件写入 `note_pipeline_events`，而不是只通过一次性的 Tauri Channel 通知前端。这样即使 WebView 刷新、详情轮询延迟或应用重新打开，用户仍然可以读取已经发生的过程。

本轮新增或统一使用的事件包括：

| 事件 | 记录时机 |
| --- | --- |
| `phaseProgress` | 阶段进度消息更新 |
| `modelCallStarted` | Provider Attempt 开始 |
| `modelRetryScheduled` | 请求失败并进入退避等待 |
| `modelCallCompleted` | 收到模型成功响应，记录耗时和返回字符数 |
| `modelCallFailed` | 当前逻辑调用最终失败，记录错误类型和耗时 |
| `contextChunkCompleted` | 一个来源分块完成并保存 |
| `contextCoverageCompleted` | 所有规划输入消息完成覆盖 |
| `outlineReady` | 结构化提纲成功生成并保存 |
| `planConfirmed` | 用户确认章节计划 |
| `sectionCompleted` | 一个章节通过验证并保存检查点 |
| `sectionFailed` | 一个章节达到上限仍未通过验证 |
| `runPaused` | 用户请求暂停 |
| `runResumed` | 从检查点继续运行 |
| `runCompleted` | 笔记和运行侧车保存完成 |
| `runFailed` | 任务进入最终错误状态 |

事件 payload 中保留阶段、请求 ID、章节 ID、尝试次数、耗时、覆盖数量、错误信息等诊断字段。详情接口最多读取最近 500 条事件，避免无限增长的日志一次性进入 WebView。

### 16.6 卡顿定位规则

当前界面将“卡顿”拆成四类，不再把所有等待都叫作模型思考：

#### A. 模型请求进行中

有 `modelCallStarted` 活动，且当前时间没有超过 `timeoutMs`。这表示网络请求仍在超时窗口内，界面显示已等待时间和剩余超时时间。

#### B. 重试退避等待

活动类型为 `retryWait`。界面显示最近错误、当前重试序号和下一次请求前的等待时间。取消会同时中断退避计时和后续请求。

#### C. 本地阶段处理

没有活动模型请求，但最近有 `phaseProgress` 或检查点事件。可能正在进行分块整理、账本合并、计划编译、章节组装或 SQLite 写入。

#### D. 事件静默

超过 30 秒没有收到新的运行事件。界面显示“没有收到新事件”，并建议从运行记录最后一项开始检查。这不直接断言发生 Bug，因为本地数据库锁、Provider 通道、WebView 事件同步都可能造成暂时静默；但它会给出明确排查起点。

### 16.7 前端界面重构

旧界面采用“输入快照栏 + 主进度卡 + 任务进度、运行预算、上下文覆盖、执行图多个右侧指标”的布局。它的问题是：

- 左侧输入信息占用固定宽度，却没有帮助判断当前卡点。
- 中央区域在提纲生成前过于空旷。
- 右侧多个指标同级排列，无法表达阶段先后。
- “上下文覆盖”和“分析知识结构”看起来像并行任务。
- 章节 `0 / 0` 缺少“尚未开始”的解释。
- 进度 Toast、中央状态和右侧状态存在重复。

本轮调整为：

```text
顶部：当前阶段 + 暂停/继续/停止
中央：当前阶段说明 + 请求诊断 + 提纲/章节内容 + 可折叠运行记录
右侧：六阶段工作流 + 输入模型信息 + 规划输入覆盖 + 预算 + 章节状态
```

主要交互变化：

- 删除原先重复的中央空状态和底部重复进度浮层。
- 没有提纲时显示“章节执行尚未开始”，明确当前仍在规划阶段。
- 右侧用纵向步骤连接线表达阶段顺序。
- 工作流步骤使用 `pending`、`active`、`completed`、`paused`、`failed` 和 `stopped` 状态。
- 运行记录默认可见，用户可以折叠；完成后仍然可以展开查看。
- 增加“复制运行诊断”按钮，用于把当前阶段、Run ID、模型、预算、活动请求和最近事件复制出来。
- 规划输入覆盖区域增加解释文本：覆盖完成不等于提纲已经生成。
- 章节进度只在提纲确认后显示，不再用 `0 / 0` 制造未定义的进度感。

### 16.8 工作流状态推导规则

前端没有根据颜色或文案猜测状态，而是根据运行详情中的事实推导工作流：

| 事实 | 对应步骤 |
| --- | --- |
| 有输入快照和预检结果 | 输入与能力预检完成 |
| `coverageComplete=true` | 准备规划输入完成 |
| 有 `planVersion.plan` | 知识结构与提纲生成完成 |
| `confirmedAt` 存在 | 语义计划确认完成 |
| 阶段进入 `assembling` 或 `persisting` | 章节执行已完成，进入保存 |
| 阶段为 `done` | 组装和保存完成 |
| 阶段为 `paused` | 当前未完成步骤显示暂停 |
| 阶段为 `error` 或 `cancelled` | 当前未完成步骤显示失败或停止 |

这种推导方式的好处是：即使前端错过某一条即时 Channel 事件，只要重新读取运行详情，工作流仍能根据持久化状态恢复正确显示。

### 16.9 本轮新增测试

新增 `deepNoteDiagnostics.test.ts`，覆盖：

1. 上下文覆盖完成但提纲规划仍进行中的状态不会被误报为章节执行。
2. 有活动模型请求时显示第几次 Attempt、已经等待时间和剩余超时窗口。
3. 持久化的模型完成事件可以转换为用户可读的耗时和响应长度。

已有验证结果：

- 前端：40 个测试文件，142 项测试通过。
- Rust：244 项测试通过。
- `cargo check` 通过。
- `cargo fmt --check` 通过。
- `npm run build` 通过。
- `git diff --check` 通过。

## 17. 当前完整运行流程示例

以截图中的 24 条消息为例，直接规划模式可能经历以下事件：

```text
preflightCompleted
phaseProgress: 上下文预检完成
contextCoverageCompleted: 24/24 条消息，mode=direct
modelCallStarted: operation=deepNote, attempt=1/1
  -> 页面显示：生成知识结构，等待模型响应
modelCallCompleted: durationMs=...
outlineReady: sectionCount=N
  -> 页面显示：等待计划确认
planConfirmed: version=1
phaseProgress: 正在扩写 1/N
modelCallStarted: 章节请求
modelCallCompleted: 章节响应
sectionCompleted: 第 1 章
  -> 重复直到所有章节完成
phaseProgress: 正在组装与检查笔记
phaseProgress: 正在保存笔记与来源
runCompleted
```

如果直接规划首次请求超时，则流程不是无限重试同一大请求，而是：

```text
modelCallStarted
modelCallFailed: Timeout
phaseProgress: 直接规划未成功，切换到分块知识账本
contextChunkCompleted: 1/5
contextChunkCompleted: 2/5
...
contextCoverageCompleted: 24/24
modelCallStarted: 基于知识账本生成提纲
```

如果在模型请求中点击暂停：

```text
runPaused
CancellationToken 中断当前请求
保存已经完成的分块、章节和预算
paused
```

继续时不会重做已经完成的分块或章节，而是从最后一个持久化检查点恢复。

## 18. 后续优化方向

本轮已经解决“看不到卡在哪里”的问题，但仍有可以继续提升的方向：

1. 为运行事件增加可选的本地诊断级别，让开发调试模式显示更详细的请求大小、估算 Token 和数据库写入耗时，正式版本保持简洁。
2. 将 `phaseProgress` 进一步规范为阶段开始、阶段完成两个事件，减少大量同类进度事件的解释成本。
3. 在模型响应成功后记录 Provider 返回的真实 usage，并与本地估算并列展示，帮助校准不同模型的 Token 估算误差。
4. 为每个章节显示来源消息 ID 和验证报告摘要，让章节失败时可以直接判断是来源不足、模型输出问题还是验证规则问题。
5. 对超过 30 秒无事件的情况增加“刷新运行详情”和“复制诊断”快捷动作，但不自动重启正在运行的模型请求。
6. 在 Release 版本中继续使用合成数据和真实会话分别验证：直接规划、分块规划、模型超时、重试退避、暂停恢复和应用重启恢复。

## 20. 本轮最终结论

深度笔记的运行状态现在可以用三个问题解释，而不再依赖一条模糊的“分析知识结构”文案：

1. **任务处于哪个阶段？** 由六阶段工作流回答。
2. **当前是否真的在调用模型？** 由请求活动、Attempt、超时窗口和 `callId` 回答。
3. **如果没有模型请求，最后完成了什么、下一步是什么？** 由持久化运行事件和工作流检查点回答。

因此，用户看到“上下文覆盖完成但仍在分析知识结构”时，可以明确知道：输入已经准备完毕，当前只是在等待提纲规划模型，不是上下文覆盖重复执行；如果超过超时或长时间没有事件，运行记录会提供具体排查位置。

## 21. 四阶段任务进度入口优化

深度笔记工作区已经能够解释单次运行的详细状态，但用户切换到 Chat、文献或设置页面后，仍然需要回到深度笔记页面才能确认任务是否推进。Chat Agent 的思考、技能和工具活动则只存在于对应消息内部，长对话中难以快速定位。为解决“后台任务存在，但缺少全局、稳定、可回到详情的入口”这一问题，本轮参考桌面开发工具的任务 Pane 结构，完成了四阶段任务进度优化。

这次优化没有增加新的任务执行引擎。Rust 深度笔记运行层、深度笔记详情、Chat 消息和流式消息 Store 仍然是唯一事实来源；新任务中心只把这些事实转换为适合全局展示的轻量投影。这样避免出现“详情页显示一个状态、全局任务入口又维护另一个状态”的双状态问题。

### 21.1 第一阶段：统一任务投影模型

新增 `TaskRunProjection`，用于统一描述 Chat Agent 和深度笔记两类任务。它不是持久化实体，也不负责调度，而是从已有运行事实即时计算出来的只读界面模型。

核心字段如下：

| 字段 | 作用 |
| --- | --- |
| `id` | 任务中心使用的稳定任务 ID，包含任务类型和来源 ID |
| `sourceId` | 原始 Chat 消息 ID 或深度笔记 Run ID，用于打开完整详情 |
| `kind` | 区分 `chatAgent` 和 `deepNote` |
| `status` | 统一后的运行、等待、暂停、完成、失败和停止状态 |
| `statusLabel` | 面向用户的状态文案，不要求用户只通过颜色判断状态 |
| `currentStepLabel` | 当前工作流步骤名称 |
| `activity` | 当前正在发生的真实活动或最近错误 |
| `startedAt`、`updatedAt`、`finishedAt` | 用于运行时长、排序和终态保留时间计算 |
| `completedCount`、`totalCount` | 用于进度计数和进度条 |
| `steps` | 可展开查看的阶段、思考、技能或工具步骤 |
| `metrics` | Tool、Skill 和 Token 等可用指标 |
| `needsAttention` | 是否等待审批、确认、恢复或错误处理 |
| `canPause`、`canResume`、`canStop` | 根据原始运行状态计算出的可用操作 |

统一任务状态映射为：

| 统一状态 | 深度笔记来源 | Chat Agent 来源 |
| --- | --- | --- |
| `running` | 可执行的 Pipeline 阶段 | Agent 工作流正在生成或调用 |
| `waiting` | 等待提纲确认或能力阻塞 | 等待 Tool 审批或用户处理 |
| `paused` | 运行已持久化为暂停 | Agent 工作流暂停 |
| `completed` | `done` | Agent 工作流完成 |
| `failed` | `error` | 失败或预算耗尽 |
| `stopped` | `cancelled` | 用户停止或 Tool 被拒绝后停止 |

深度笔记在任务中心仍采用详情页相同的六阶段语义：

```text
输入与能力预检
准备规划输入
生成知识结构与提纲
确认语义计划
生成并验证章节
组装并保存笔记
```

任务中心直接复用 `buildDeepNoteWorkflow`，因此不会为同一运行维护第二套阶段判断。上下文覆盖完成但提纲尚未返回时，前两步显示完成，第三步显示运行中，不会再让“上下文覆盖”和“生成知识结构”看起来像两个互相冲突的并行任务。

### 21.2 第二阶段：右上角紧凑任务入口与展开面板

新增全局 `TaskCenter`。只有存在真实任务投影时，右上角才显示入口；没有深度笔记运行，也没有真实 Agent 活动时，不占用界面空间。

收起状态提供以下信息：

- 当前最高优先级任务的状态图标。
- 当前步骤，或正在运行、最近保留的任务数量。
- 已完成步骤数和总步骤数。
- 已运行时间。

展开面板提供以下信息：

- 多任务切换列表。
- 任务标题、状态和已用时。
- 真实步骤进度和当前活动。
- Tool、Skill 和 Token 指标。
- 深度笔记六阶段计划。
- Chat reasoning、Skill 和 Tool 步骤。
- 可渐进展开的思考内容和 Tool 结果预览。
- 暂停、继续、停止和完整详情操作。

界面采用固定上限宽度和视口高度约束，小窗口下入口收缩为 40px 图标按钮。状态同时使用图标、文字和颜色表达；工作区身份色用于区分 Chat 与深度笔记，成功、警告和失败仍使用独立语义色。面板保持 5 至 7px 圆角、Lucide 图标、单层工具面板结构，没有加入卡片墙、玻璃效果或装饰渐变。

### 21.3 第三阶段：接入深度笔记、Chat 详情和终态折叠

深度笔记任务入口直接接入现有运行控制：

- 运行中的可中断阶段显示“暂停”。
- 暂停状态显示“继续”。
- 未进入终态的任务显示“停止”。
- “完整详情”切换到深度笔记工作区，继续使用已有诊断、日志、预算和章节视图。

Chat Agent 任务严格遵守真实活动原则。只有消息中存在以下任意事实时，才建立 Chat 任务投影：

- 模型返回了 reasoning。
- 运行层真实激活了 Skill。
- 运行层产生了 Tool Trace。

普通 Chat 文本生成不会为了占满任务面板而虚构“规划、执行、反思”等步骤。当前模型不支持 reasoning 或 Tool 时，任务中心也不会伪造对应活动。

Chat 的“完整详情”会切换回 Chat 工作区，并通过消息元素的稳定 `message-{id}` 锚点定位到对应消息。完整 reasoning、Skill 和 Tool 工作流仍由消息内部原有界面展示，任务中心只提供可扫描摘要和返回路径。

当所有活跃任务进入完成、失败或停止状态后，展开面板自动折叠，避免完成后的工作流长期遮挡内容。终态入口不会立即消失，而是在 15 分钟内保留，用户可以重新打开检查结果、失败位置或过程内容；保留时间到期后，投影自然消失，不需要额外清理持久化数据。

### 21.4 第四阶段：多个后台任务聚合展示

任务中心支持同时聚合深度笔记和 Chat Agent。当前界面允许两类运行事实同时存在，例如深度笔记在后台生成章节时，用户在 Chat 中执行带 reasoning 或 Tool 的任务。

多个任务按照“是否需要用户处理”和“运行紧迫性”排序：

```text
等待处理 -> 失败 -> 暂停 -> 运行中 -> 已停止 -> 已完成
```

同一状态下，最近更新的任务排在前面。这个顺序确保 Tool 审批、提纲确认、失败和暂停任务不会被持续输出的普通运行任务挤到后面。面板顶部显示活跃任务数量，列表显示每个任务的类型、标题、当前步骤和状态图标；选择任务只改变面板投影，不修改原始执行状态。

### 21.5 流式性能边界

Chat reasoning 可能以高频增量到达。若在 `App` 根组件订阅流式 Store，每次 reasoning 增量都可能让应用壳、侧栏、工作区 Provider 和大量派生数据重新渲染。本轮将 `useStreamingMessage` 订阅限制在 `TaskCenter` 内部，根组件只传入最后一条助手消息的稳定数据。

这样可以让任务入口及时更新 reasoning，同时把最高约 30 FPS 的流式重渲染限制在一个紧凑组件内。任务计时器只在存在活跃任务时每秒更新；全部任务进入终态后停止周期计时，仅为最近终态的到期时间设置一次定时器。该设计避免为了显示已用时而让整个应用永久每秒重渲染。

Chat 是否运行由目标助手消息的 `pending`、`streaming` 状态和对应流式 Store 条目决定，不直接使用全局 `requestInFlight`。因此执行上下文压缩等其他请求时，不会把一条已经完成的历史 Agent 消息错误投影为“运行中”。

### 21.6 自动折叠与状态恢复规则

任务中心记录上一轮仍处于非终态的任务 ID 集合。当这个集合从非空变为空时，面板自动关闭。自动关闭只改变面板的本地展开状态，不删除任务、日志、消息或深度笔记检查点。

当前选择的任务消失时，组件自动选择排序后的第一项；任务列表为空时，同时清空选择并关闭入口。用户按 `Escape` 或点击面板外部也可以关闭。切换页面不会中断后台运行，因为任务控制仍由原始 Chat Runtime 和深度笔记 Runtime 负责。

### 21.7 测试覆盖

新增任务投影测试覆盖以下关键边界：

1. 普通 Chat 文本不会产生虚构任务。
2. 真实 reasoning 会产生可查看内容的 Chat Agent 任务。
3. 等待审批的 Tool 会映射为 `waiting` 和 `needsAttention=true`。

## 22. 四阶段优化后的完整使用流程

深度笔记和 Chat Agent 同时存在时，用户看到的流程为：

```text
运行层产生真实任务状态
  -> 投影层统一状态和步骤
  -> 右上角入口显示最高优先级任务
  -> 展开后可切换多个任务
  -> 需要时暂停、继续或停止深度笔记
  -> 点击完整详情回到深度笔记诊断页或具体 Chat 消息
  -> 所有任务结束后面板自动折叠
  -> 终态入口保留 15 分钟供复查
```

这套结构将“随时知道后台任务进行到哪里”和“进入完整页面诊断具体卡点”分成两个层次：右上角入口负责全局可见性和快速控制，深度笔记页与 Chat 消息工作流负责完整事实和诊断。两层都读取同一运行事实，因此不会因为新增全局进度入口而引入第二套执行状态。

## 23. 右侧运行详情独立滚动修复

深度笔记右侧运行详情会依次展示工作流、输入与模型、规划输入覆盖、运行预算、章节进度和执行图。内容超过窗口高度时，原样式虽然声明了 `overflow: auto`，但缺少完整的 Grid 收缩边界和清晰的滚动条样式。在 WebView2 使用覆盖式滚动条或窗口高度较小时，用户难以判断下方仍有内容，右侧也可能表现得像被窗口底部截断。

本轮补充了以下滚动约束：

- 深度笔记根 Grid 增加 `min-height: 0` 和 `overflow: hidden`，确保第二行始终受工作区可用高度约束。
- 右侧 `.deep-note-run-pane` 增加 `min-width: 0`、`min-height: 0`，允许它在 Grid 中正确收缩。
- 将右侧滚动方向明确为 `overflow-y: auto` 和 `overflow-x: hidden`，防止长模型 ID 等内容产生横向滚动。
- 增加 `overscroll-behavior: contain`，滚动到边界时不把滚轮事件继续传递给外层工作区。
- 增加 `scrollbar-gutter: stable`，滚动条出现时不会挤压指标行和文字。
- 为 WebView2 补充可辨识的滚动轨道、滑块和悬停状态，同时保留 Firefox 的 `scrollbar-color` 与 `scrollbar-width` 声明。
- 主内容区同步增加 `min-height: 0`，保证左右两个滚动区域都服从同一个工作区高度。

修复后，右侧面板独立滚动，顶部应用栏和中央内容不会随之移动；当右侧存在更多预算、章节或执行图信息时，用户能够通过持续可见的滚动条识别并访问这些内容。

## 24. 深度笔记模型信息与失败恢复入口

右侧原先把内部稳定 ID 直接作为“模型”值展示，例如 `model-fb7484ef-18af-4026-8b2e-d912ce8a566d`。这个 ID 只适合本地数据关联，不适合帮助用户判断实际使用的是哪家服务、哪个模型，也无法在请求失败时指导恢复。

本轮改为从深度笔记预检快照和模型设置中组合展示：

- `服务商`：显示用户配置的 Provider 名称。
- `模型`：显示用户在设置中配置的 `displayName`。
- `API 标识`：显示实际发送给 Provider 的 `apiModel`，用于排查中转站映射和模型别名问题。
- 内部 `providerId`、`modelId` 仍保留为无显示名称时的兜底值，不再作为正常界面的唯一信息。

当运行进入 `error` 终态时，右侧增加“模型请求失败”恢复区。它只列出已启用且已配置 API Key 的模型，用户可以选择备用模型并点击“切换并重新开始”。该动作按顺序执行：

```text
保存新的深度笔记模型配置
  -> 使用当前会话重新创建深度笔记运行
  -> 重新执行输入预检和规划流程
  -> 右侧模型信息更新为新的 Provider、显示名称和 API 标识
```

切换不会偷偷替换模型，也不会在请求失败时自动重试另一个 Provider。只有用户明确选择并确认“切换并重新开始”后，才会改变深度笔记专用模型配置并启动新的运行。没有其他已配置 API Key 的模型时，界面明确提示用户先到设置页完成 Provider 和 API Key 配置。

## 25. “生成知识结构与提纲”连续 HTTP 504 的根因与修复

### 25.1 真实运行记录说明了什么

本轮没有只根据界面上的“504”猜测，而是只读检查了 Release 实例保存的深度笔记运行、事件和用量记录。失败样本的事实如下：

- 输入包含 24 条消息、0 个附件，估算输入约 58,168 Token。
- 输入已经拆成 5 个来源分块，5/5 分块全部成功，24/24 条消息均已进入知识账本。
- 失败发生在分块之后的“知识账本汇总为最终提纲”请求，不是输入读取、分块、数据库保存或前端状态同步失败。
- 最终提纲请求配置为初次请求加 5 次自动重试，共发出 6 次相同请求。
- 六次请求都在约 60 秒后由中转服务返回 HTTP 504，总调用耗时约 373 秒。
- 最终错误分类为 `Timeout`，HTTP 状态为 `504`；应用自身的单次超时窗口是 240 秒，因此不是 Mnemora 在 60 秒时主动取消请求。
- 相同 Provider 和模型在此前的来源分块请求中能够成功返回，说明模型配置、API Key 和基本网络链路是通的。

因此，这不是“整个工作流没有打通”。已经打通并成功完成的是：

```text
输入快照
  -> 上下文预算
  -> 来源分块
  -> 分块模型提取
  -> 知识账本持久化
  -> 24/24 消息覆盖完成
```

真正缺失的是最终提纲请求的自适应恢复分支。旧逻辑在长上下文场景下已经有分块账本，却在最终汇总请求收到 504 后，仍然按照全局重试次数重复发送同一份请求；五次重试不会缩小输入、降低输出预算或改变提纲规模。换言之，重试机制已经工作，但恢复策略没有形成闭环。

### 25.2 为什么同一个模型能够完成分块，却总在最终提纲处失败

旧版来源分块和最终提纲请求的负载不同：

| 请求 | 输入 | 旧输出上限 | 结果 |
| --- | --- | ---: | --- |
| 来源分块提取 | 单个来源块 | 4,096 Token | 多次成功 |
| 最终提纲汇总 | 聚合后的完整知识账本 | 8,192 Token | 六次 HTTP 504 |

最终提纲不是简单读取一段文本。模型需要同时完成主题聚类、章节组织、依赖关系设计、证据来源分配和严格 JSON 输出。旧逻辑允许 1 至 40 个章节，并为该调用保留最多 8,192 个输出 Token。对于存在约 60 秒网关限制的中转服务，这种请求更容易在完整响应返回前被网关终止。

这里要区分两个超时边界：

- Mnemora 的 `attempt_timeout=240s` 是客户端最多愿意等待多久。
- HTTP 504 是中转服务或它上游的网关已经提前放弃等待。

把客户端超时从 240 秒继续调大不能解决一个约 60 秒就主动返回 504 的网关；真正有效的方向是降低单次汇总负载、限制输出规模，并在失败后改用更小的请求，而不是重复原请求。

### 25.3 第一轮运行层修复

第一次针对 504 的修复先对提纲阶段增加以下约束和恢复路径：

1. 最终提纲输出上限从 8,192 Token 收紧到 4,096 Token。
2. 来源分块提取和分块 JSON 修复的输出上限收紧到 2,048 Token，避免局部提取产生不必要的长响应。
3. 提纲提示明确优先生成 6 至 12 个章节，且不得超过 12 个章节；Rust 的最终结构校验仍然保留。
4. 上下文预算中的提纲输出预留同步改为 4,096 Token，预算计算与实际请求保持一致。
5. 最终提纲请求遇到 HTTP 504 时不再重复发送同一份重型请求，而是立即构造“精简知识账本”进入恢复调用；其他可恢复的连接或 Provider 错误仍遵循用户配置的自动重试次数。
6. 精简账本保留可追溯的分块摘要、核心术语、事实、主题、冲突、开放问题和全局约束，但限制每一类条目数量与单条长度。
7. 精简恢复调用把输出上限进一步收紧到 3,072 Token，最多重试 1 次。
8. 精简恢复仍使用原模型和原 Provider，不会静默替换用户选择的模型。
9. 如果普通汇总和精简汇总都失败，任务进入明确的 `error` 终态，由用户在右侧选择备用模型并重新开始。

新的控制流为：

```text
来源覆盖完成
  -> 4,096 Token 上限生成提纲
  -> 成功：Rust 解析和校验提纲
  -> HTTP 504：不重复原请求，立即降载
  -> 其他 Timeout / Connection / Provider / ContextLengthExceeded：重试耗尽后降载
       -> 压缩知识账本
       -> 3,072 Token 上限精简生成
       -> 成功：Rust 解析和校验提纲
       -> 仍失败：保留完整错误并等待用户选择备用模型
```

这组数值记录的是第一轮降载方案，不是当前最终常量。后续继续使用 24 条消息样本测试后，发现即使建立了降载分支，提纲请求的输出预算仍可以进一步收紧，因此当前实现继续调整为：提纲总预算上限 2,048 Token，快速提纲和精简恢复为 1,024 Token；来源分块摘要仍保留 4,096 Token，防止证据 ID 和结构化摘要在中途被截断。第 28.8 节记录了从第一轮 4,096/3,072 到最终 2,048/1,024 的继续收敛过程。

### 25.4 进度和诊断信息修复

旧界面把来源分块、知识账本汇总和最终提纲生成都显示成“正在分析知识结构”，导致用户无法判断当前究竟卡在哪里。本轮为真实模型调用增加了阶段标识：

- `deepNoteChunk`：来源分块提取。
- `deepNoteChunkRepair`：来源分块 JSON 修复。
- `deepNoteOutlineDirect`：上下文在预算内时直接生成提纲。
- `deepNoteOutline`：从完整知识账本生成提纲。
- `deepNoteOutlineFallback`：使用精简知识账本恢复提纲。

运行事件还会记录以下非敏感诊断指标，不保存 Prompt 正文：

- `inputChars`
- `systemPromptChars`
- `maxOutputTokens`
- `maxRetries`
- `timeoutMs`
- `statusCode`
- `providerCode`
- `retryAfterMs`

前端运行记录会显示具体模型阶段、输入字符数、返回字符数、输出上限和耗时。下一次出现失败时，可以直接区分“来源分块失败”“完整账本汇总失败”和“精简恢复失败”，不再只能看到一个笼统的 `deepNote` 调用。

### 25.5 仍需通过 Release 实测确认的边界

本轮已经修复重复发送同一重型请求而没有恢复策略的问题。默认“自动重试 5 次”的全局设置没有被取消，但对于提纲汇总阶段已经明确收到的 HTTP 504，继续发送相同请求不会增加成功概率，只会再等待多个约 60 秒的网关周期。因此运行层会让该类错误跳出普通重试循环，直接使用精简账本；来源分块以及非 504 的可恢复错误仍保持原有重试语义。

HTTP 504 的最终决定方仍是用户配置的中转服务。如果新版本在更小的输入和输出预算下仍稳定在约 60 秒返回 504，则说明该 Provider 对非流式长请求存在固定网关限制。届时应依据新事件中的请求规模和耗时，评估将深度笔记的纯文本模型调用改为“内部流式接收、运行层聚合完整 JSON”的第二阶段方案；不能仅继续增加客户端超时时间或重试次数。

当前修复优先保持现有 Provider 适配和严格 JSON 校验路径，先用真实 Release 数据验证负载收敛是否足以消除 504，再决定是否引入新的流式聚合通道。

## 26. 已暂停、已停止和失败任务的恢复闭环

### 26.1 原问题不是缺少按钮，而是状态契约互相冲突

旧实现已经保存了深度笔记的输入快照、来源分块、知识账本、提纲、章节正文和运行事件，但后端、前端与 SQLite 对“哪些状态还能恢复”的理解不一致：

- Rust 运行层能够识别部分失败状态，但前端只允许 `paused` 调用继续。
- 前端收到 `error` 或 `cancelled` 后会清空当前 Run 引用，页面因此退化成“消息 0、附件 0、模型 -、运行记录 0 条”。数据库中的真实检查点并没有消失，只是界面失去了关联 ID。
- SQLite 的唯一索引仍把 `error` 视为该会话的占用任务。用户直接再次创建时会得到“已有可恢复任务”，但前端收到错误后又清空页面，形成无法继续、无法重试、也无法重新生成的恢复死锁。
- `cancelled` 没有进入应用启动时的可恢复任务查询。用户重启应用后，停止任务仍在数据库中，却无法重新附着到任务中心和深度笔记页面。
- 章节已经用完 5 次节点尝试或 5 次语义修订后，若只把 Run 状态改回运行中，执行器会立即再次判断预算耗尽，所以“继续”看似执行，实际不会产生新的有效尝试。
- DAG 节点状态通过 Serde 以 camelCase 保存，例如 `needsReview` 和 `needsRevision`；旧重置 SQL 只匹配 snake_case，导致这些失败节点没有真正回到 `pending`。

因此，本轮把恢复设计成明确的状态机操作，而不是在同一个“继续”按钮里猜测用户意图。

### 26.2 四种操作的语义边界

| 当前状态 | 用户操作 | 是否复用原 Run | 保留内容 | 重置内容 |
| --- | --- | --- | --- | --- |
| `paused` | 继续 | 是 | 全部检查点、预算和尝试次数 | 不重置 |
| `cancelled` | 从检查点继续 | 是 | 已完成章节、提纲、知识账本、来源分块 | 不重置失败计数 |
| `error` / `blocked` | 重试失败步骤 | 是 | 已完成章节及其证据 | 失败章节和失败 DAG 节点 |
| `error` / `blocked` / `cancelled` | 重新生成 | 否 | 旧 Run 作为诊断记录保留 | 使用当前会话和当前模型创建全新 Run |

“继续”和“重试”都不是重新执行整个任务。运行层根据持久化检查点判断下一步：

```text
没有提纲
  -> 回到知识结构与提纲生成

已有提纲、尚未选择章节
  -> 回到提纲确认

已有提纲和章节选择
  -> 保留完成章节，只调度未完成或被重置的章节
```

“重新生成”则先把旧失败 Run 终结为 `cancelled`，释放会话唯一索引，再通过正常的 `start` 流程重新执行模型能力预检、输入快照建立和规划。新 Run 使用设置页当前保存的深度笔记模型，因此用户在失败恢复区切换模型后，实际执行顺序为：

```text
保存用户选择的模型
  -> 终结旧 Run
  -> 用当前会话创建新 Run
  -> 重新预检模型能力
  -> 重新建立输入快照和语义计划
```

运行层不会静默更换 Provider，也不会把旧模型生成的规划和新模型的新输入混在同一个 Run 中。

### 26.3 输入快照一致性保护

从原检查点继续前，运行层会重新读取会话并比较以下快照字段：

- 会话修订时间；
- 纳入任务的消息 ID；
- 附件 ID；
- 根据附件 ID、名称、大小和路径计算的附件内容标识；
- 选中的文献 ID；
- 选中的笔记 ID。

只要任一字段发生变化，继续或失败步骤重试都会被拒绝，并明确要求“使用当前内容重新生成”。这是为了防止旧知识账本引用旧消息、而新章节读取新会话所造成的证据错位。此时用户仍能看到旧 Run 的详情和日志，也可以主动选择重新生成；应用不会删除旧检查点或假装已经在新上下文中恢复。

### 26.4 人工恢复预算

自动重试和人工恢复是两个不同的预算：

- 单次模型请求仍遵循设置中的自动重试次数，默认最多重试 5 次。
- 同一个深度笔记 Run 最多允许 5 次人工恢复。`executionVersion` 初始为 1，每次从停止点继续或重试失败步骤都会加 1；到达 5 次人工恢复后，界面要求重新生成新 Run。
- 每次人工恢复会在当前已用语义调用数的基础上增加 12 次调用余量，总上限为 200，避免旧 Run 因全局语义预算已经耗尽而立即再次失败。
- “重试失败步骤”将失败章节的 `attemptCount`、`revisionCount`、部分正文、失败证据和验证结果清零，同时重置 `failed`、`blocked`、`needsReview`、`needsRevision`、`interrupted` DAG 节点。
- 已完成章节的正文、尝试次数、修订次数、证据和验证结果全部保留，不为一次局部失败付出全量重算成本。

### 26.5 重启应用后的任务发现规则

可恢复任务查询现在包含尚未生成笔记的 `cancelled` Run，但不会把所有历史停止记录重新塞回任务中心。每个会话只考虑创建时间最新的 Run：

- 最新 Run 是活动、暂停、阻塞、失败或尚未产出笔记的停止状态时，允许重新附着。
- 最新 Run 已经 `done` 时，不再恢复更早的停止或失败 Run。
- 已停止但已经产出部分完成笔记的 Run 不作为未完成任务恢复，因为它已经通过 `done + degraded` 路径保存为可见草稿。
- 发现 `paused`、`cancelled`、`error` 或 `blocked` 时只恢复界面状态，等待用户明确选择继续、重试或重新生成，不自动消耗模型调用。
- 发现应用退出时遗留的活动状态时，运行层按持久化阶段重新调度；若同一 Run 仍在当前进程中运行，前端进入只读轮询并持续刷新真实状态。

新建任务若遇到“该会话已有可恢复任务”，前端会立即重新查询可恢复 Run，并按会话 ID 重新附着，而不是清空页面。即使创建命令在“数据库已经写入 Run、后台任务尚未成功启动”的窄窗口失败，用户仍能看到原 Run、模型、输入统计、事件和恢复入口。

### 26.6 页面与任务中心操作

深度笔记页面和右上角任务中心采用同一套能力投影：

- `paused`：显示“继续”。
- `cancelled`：显示“从检查点继续”和“重新生成”。
- `error` / `blocked`：显示“重试失败步骤”和“重新生成”。
- 模型请求失败：右侧保留实际 Provider、模型显示名称与 API 标识，并允许用户选择已配置的备用模型后重新生成。

错误和停止事件不再调用统一的 `finishDeepNoteRun()`。该函数只用于真正完成并已持久化笔记的终态。失败后 Run ID、详情刷新、章节进度、运行预算和事件日志继续保留，因此恢复操作拥有完整上下文。

运行记录新增三类可读事件：

- `runContinued`：从停止检查点继续，记录新的执行版本。
- `runRetryRequested`：重试失败步骤，记录执行版本和是否重置失败章节。
- `runRestarted`：旧 Run 已触发重新生成，并记录新 Run ID。

### 26.7 回归测试边界

本轮增加或补强以下自动化验证：

- 停止且未产出笔记的 Run 能在应用重启后被发现。
- 同一会话存在更新的完成 Run 时，不恢复更旧的停止 Run。
- `executionVersion` 随人工恢复递增，第 6 次人工恢复被拒绝。
- 已完成章节在失败步骤重试后保持正文和尝试统计不变。
- 失败章节回到 `pending`，正文、尝试次数和修订次数清零。
- camelCase 的 `needsReview` DAG 节点能够正确重置。
- 会话内容变化后拒绝混用旧输入快照。
- 任务中心对失败 Run 投影出 `canRetry + canRestart`，对停止 Run 投影出 `canResume + canRestart`。
- 三种恢复事件能够在诊断日志中显示可理解的中文说明。

这套恢复闭环的目标不是保证任何 Provider 错误都能自动成功，而是保证每一次暂停、停止和失败都有明确的下一步，且所有已完成工作、失败位置和模型诊断信息都不会因为前端清空引用而消失。

## 27. 中转站超时、限流与真实全链路诊断优化

### 27.1 错误不再统一归类为“模型请求失败”

本轮将模型调用错误进一步区分为客户端等待超时、上游网关超时、普通限流、账户并发限制、Provider 无可用渠道、认证失败、余额或配额不足、连接失败、上下文超限和结构化输出错误。HTTP 429 中包含 concurrency/capacity 的响应被识别为账户并发限制；HTTP 502、504、524 识别为上游网关超时；HTTP 503 中包含 unavailable/no available channel 的响应识别为 Provider 暂时不可用。

延长客户端等待只能缓解“模型仍在计算但本地等待窗口先结束”的情况。中转站主动返回 429、503、504 或 524 后，连接已经终止，继续增加客户端超时时间不会让原请求恢复。因此运行层为不同阶段配置了不同等待窗口，并为不同错误选择不同后续动作。

### 27.2 阶段化超时与重试

| 阶段 | 单次等待窗口 | 失败策略 |
| --- | ---: | --- |
| 来源分块提取 | 300 秒 | 临时网络错误可重试；保留已完成分块 |
| 来源 JSON 修复 | 180 秒 | 只修复当前分块 |
| 直接提纲 / 账本提纲 | 300 秒 | 上游超时切换精简账本，不原样重复 |
| 精简提纲 | 180 秒 | 失败后保留账本并进入可恢复错误状态 |
| 章节生成 | 420 秒 | 只重试当前章节，保留完成章节 |

429 账户并发限制使用 15 秒起步的指数退避，单次等待上限 120 秒，并优先采用服务端 Retry-After。503 无可用渠道不再连续重试同一个模型，直接提示用户选择备用模型。504/524 提纲请求不再原样重放，而是缩小请求或返回检查点恢复入口。

### 27.3 真实测试中定位出的两个本地流程缺陷

第一，旧的“可直接规划”阈值为 24000 Token，只保证提纲请求能够装入上下文，没有保证章节生成还能重新加载相同来源。直接提纲成功后，如果章节引用的原始消息超过单章 3000 Token 上限，而运行中又没有分块知识账本，章节会以“没有可加载来源”失败。现在直接模式阈值与章节原始来源预算对齐为 3000 Token；更大的输入先生成带真实消息 ID 的知识账本，章节阶段始终有可追溯的摘要回退。

第二，生成提纲和确认提纲时会重新初始化语义调用预算，导致分块与提纲已经消耗的调用没有被正确纳入章节阶段，或者章节只得到固定的 3 次空间。现在预算会保留已经使用的调用，并按每个章节的首次生成加最多 5 次语义修订预留空间；人工恢复仍遵循独立的执行版本和恢复上限。

## 28. 从发现问题到修复完成的完整过程复盘

本节按照实际开发顺序记录每一次问题是如何被发现、如何定位、采取了什么方案、方案解决了什么、又暴露了什么新的边界。这里不把最终代码倒叙成一套看起来一次完成的设计，因为深度笔记的问题不是一次改动解决的，而是经过多轮真实使用、Release 安装、模拟测试和错误响应分析后逐步收敛的。

### 28.0 Git 历史中的架构演进节点

以下节点来自当前仓库的 Git 历史，用来区分“最初设计”“上一轮已发布修复”和“本轮继续修复”，避免把不同版本的行为混写成一个版本的能力：

| 提交 | 版本/阶段 | 主要变化 | 暴露出的后续问题 |
| --- | --- | --- | --- |
| `3c73e90` | 深度笔记第一版 | 建立提纲、章节生成、组装、持久化和笔记编辑 | 依赖单次大请求，没有分块、请求级进度和恢复闭环 |
| `8e6af34` | 附件能力和 Plan09 设计阶段 | 明确模型能力边界，并记录 Plan-and-Execute / DAG 方向 | 规划结构确定后，执行检查点和错误恢复仍不完整 |
| `ad5c76c` / `v0.1.11` | 深度笔记加固 | 增加 Token 预算、上下文压缩、分块账本、阶段状态和部分恢复能力 | 真实慢 Provider 下仍可能重复发送大提纲请求；失败后前端 Run 引用仍可能丢失 |

从这个历史可以看出，后续问题并不是前一轮完全没有解决，而是每次把系统从“短任务可用”推进到“长任务可观测”后，才会暴露下一层状态和边界问题。文档后面的每一个阶段都对应这条演进链中的一个实际缺口。

### 28.1 第一阶段：最初的深度笔记管线能够工作，但没有长任务基础设施

深度笔记第一版是在提交 `3c73e90 feat: complete deep note pipeline and note editing` 中建立的。最初的管线已经具备以下能力：

1. 从当前会话读取已完成消息。
2. 调用一次分析模型生成提纲。
3. 将提纲展示给用户确认。
4. 按章节调用模型生成 Markdown 正文。
5. 组装章节并持久化为笔记。
6. 保存章节来源和笔记编辑提案。

这套设计适合短对话，但它隐含了几个没有被显式处理的假设：

- 完整会话可以一次性放进模型上下文。
- 一次请求失败时，重新发送原请求有机会成功。
- 用户取消通常发生在阶段之间，而不是发生在一次网络调用内部。
- 只要前端显示“正在分析”，用户就能理解任务进展。
- 章节和提纲只需要内存中的临时状态，不需要可恢复检查点。

这些假设在短样本上不会立即暴露，所以第一版的基础功能测试可以通过；但它们不适用于长对话、慢中转站和需要十几分钟才能完成的任务。

### 28.2 第二阶段：发现 300,000 字符截断造成“看起来成功、实际上遗漏”

早期实现使用 `MAX_TRANSCRIPT_CHARS = 300_000` 对转写结果做字符截断。它的直接目的，是防止把超大的字符串一次性交给模型，也避免 WebView 和 Rust 同时持有过大的临时文本。

但是，这个保护产生了更严重的语义问题：

1. 前端和用户看不到哪些消息被截断。
2. 模型没有被告知输入是不完整的。
3. 笔记可以正常生成并保存，因此表面上是“成功”状态。
4. 来源记录没有办法证明笔记覆盖了哪些消息。
5. 同一会话的后半段内容可能完全没有进入模型，但正文仍然使用肯定语气。

因此，单纯把字符上限调大不是正确修复。字符不是上下文的稳定单位，中文、英文、代码、JSON、引用和图片输入的 Token 比例都不同；而且“截断后继续生成”违反了深度笔记必须可追溯的要求。

本阶段的解决方案是把“截断”改造成“显式预算和覆盖率”问题：

- 估算每条消息的 Token 数量。
- 保存纳入任务的消息 ID。
- 把过长会话拆成多个来源分块。
- 每个分块完成后保存摘要和真实来源消息 ID。
- 只有所有分块都完成，才允许生成提纲。
- 如果有遗漏，任务必须进入明确错误或阻塞状态，不能伪装成完整笔记。

解决后得到的改进是：任务可以说明“已处理 24/24 条消息”，而不是只说“分析完成”。新的问题也随之出现：分块本身需要调用模型，分块调用会增加请求数；如果没有共享预算，章节阶段可能在提纲完成后才发现额度已经耗尽。

### 28.3 第三阶段：引入 Token 预算后，发现“窗口比例”仍然不够

普通 Chat 早期主要按上下文窗口的固定比例触发压缩。这个方案看似简单，但没有同时扣除：

- System Prompt；
- Skill 正文；
- Tool Schema；
- 过去的 Tool Call 和 Tool Result；
- 图片或其他附件的视觉输入；
- 本轮最大输出；
- Provider 协议包装和估算误差。

结果是前端判断“尚未超过窗口”，Provider 却返回 `context_length_exceeded`。深度笔记如果沿用同样规则，会在长分析请求中发生更难定位的失败。

本阶段形成了统一的后端预算公式：

```text
可用输入预算 = 模型上下文窗口
              - 本轮最大输出预算
              - System/协议固定开销
              - Tool/Skill/附件开销
              - 安全余量
```

预算由 Rust 运行层最终裁决，前端的 Context Usage 只负责展示。这样做的原因是前端估算不能替代发送前的最后一道门禁，尤其是模型能力、Provider 协议和工具契约都由后端决定。

优化后的新边界是：Token 估算仍然不是真实 Tokenizer。它是保守估算，不保证和每个 Provider 的计费 Token 完全一致，所以必须保留安全余量，并把最终的 Provider 上下文错误继续保留为一种可诊断错误，而不能假定本地预算已经百分之百正确。

### 28.4 第四阶段：Plan09 引入 Plan-and-Execute 与 DAG，但执行层仍需要检查点

在 `09-深度笔记Plan-and-Execute与DAG实施计划.md` 中，深度笔记从单次生成改成了“先计划、再执行”的结构。当前运行模型包含：

```text
输入快照
  -> 预检和能力确认
  -> 知识结构分析
  -> 提纲生成
  -> 用户确认章节
  -> DAG 计划编译
  -> 章节执行
  -> 章节验证和必要修订
  -> 笔记组装
  -> SQLite 持久化
```

章节之间通过 `dependsOn` 表达依赖，运行层用拓扑顺序判断哪些节点可以执行。每个章节记录状态、尝试次数、修订次数、证据 ID、验证结果和错误信息。

这一步解决了两个问题：

1. 用户可以在模型真正扩写前修改提纲，而不是只能接受模型一次性生成的正文。
2. 一个章节失败时，可以保留其他已经完成的章节，不必把整篇笔记全部重算。

但 Plan-and-Execute 和 DAG 只解决了“任务如何组织”，没有自动解决“任务如何恢复”。当时仍然存在以下缺口：

- 运行状态和章节检查点没有统一的恢复协议。
- 前端在失败后清理当前 Run 引用，导致数据库里有任务，界面却找不到。
- `error`、`cancelled`、`paused` 的语义没有完全统一。
- 重新执行可能重复已完成章节。
- 语义调用预算在分析阶段和章节阶段之间被重新初始化。

因此，Plan-and-Execute 不是本次问题的终点，而是后续恢复闭环的基础。

### 28.5 第五阶段：真实 Release 使用暴露“建立输入快照与语义计划”长时间不动

在正式 Release 中使用真实会话生成深度笔记时，用户观察到界面长期停留在“建立输入快照与语义计划”或“分析知识结构”。这并不等于单一 bug，因为同一文案可能对应多个不同状态：

| 用户看到的现象 | 实际可能发生的事情 |
| --- | --- |
| 文案长时间不变 | 正在读取会话或建立快照 |
| 文案长时间不变 | 正在等待中转站首字节 |
| 文案长时间不变 | 当前请求已经失败，正在退避 |
| 文案长时间不变 | 正在重复发送同一份大请求 |
| 文案长时间不变 | JSON 解析失败，正在修复 |
| 文案长时间不变 | 用户点击取消，但 HTTP Future 仍未结束 |

根因不是文案本身，而是缺少请求级可观测状态。旧前端只有 `preflight`、`analyzing`、`drafting` 等粗粒度 Phase；后端也没有把调用 ID、操作名、尝试次数、超时窗口、最近错误和退避时间持久化。

解决过程分为四步：

1. 在运行层增加 `NotePipelineActivity`，记录当前调用的 `operation`、`callId`、`attempt`、`maxRetries`、`timeoutMs`、`delayMs` 和 `lastError`。
2. 在模型调用完成或失败时追加 `modelCallCompleted` / `modelCallFailed` 事件。
3. 在退避等待时追加 `retryWait` 活动，而不是让界面看起来像冻结。
4. 前端把这些事件投影到右上角任务中心和深度笔记详情，显示“来源分块提取”“知识账本汇总提纲”“精简账本提纲”“章节生成”等真实阶段。

这样修复后，用户可以区分“仍在工作”和“确实失败”。但是事件可观测性也带来新的设计约束：事件不能保存完整 Prompt、API Key 或大段附件正文，否则诊断日志会变成新的内存和隐私负担。因此当前只记录字符数、Token 预算、状态码、错误分类和耗时，不记录请求正文。

### 28.6 第六阶段：取消操作从“阶段标志”改成贯穿 Future 的 CancellationToken

旧实现的取消主要是设置一个状态，后台任务在章节循环或阶段边界读取它。若模型调用本身正在等待网络，取消不会立即终止等待。

修复后的调用链是：

```text
取消按钮
  -> note_pipeline_cancel
  -> AppState 中的运行注册表
  -> CancellationToken.cancel()
  -> chat_service::complete_with_execution
  -> tokio::select!
       - 当前 HTTP/模型请求
       - 单次调用超时
       - CancellationToken
  -> 更新 cancelled / paused 检查点
```

每个重试退避也必须监听同一个取消令牌。否则模型请求虽然能取消，15 秒或 120 秒的退避仍然会让用户感觉按钮没有反应。

这一修复解决了“点击取消却继续等待”的问题，但引入了终态语义的取舍：

- 如果已经完成了部分章节，取消后可以保存为可见草稿。
- 如果没有完整笔记，任务必须保留检查点和恢复入口。
- 取消不能被当成普通错误，也不能因为前端收到了取消事件就删除 Run ID。

这也是后续前端恢复闭环必须保留 `cancelled` 状态的原因。

### 28.7 第七阶段：真实 HTTP 错误揭示问题在中转站，而不只是本地超时

真实 Provider 测试中出现了多种响应：

- `401 Invalid token`：认证失败。
- `403 balance/quota/insufficient`：余额或额度不足。
- `429 concurrency/capacity`：账户并发额度不足。
- `503 no available channel`：当前模型没有可用渠道。
- `504`、`524`：中转网关或上游服务已经超时。

旧逻辑如果只把这些都归类为“请求失败”或“超时”，用户无法知道应该等待、换模型、检查余额，还是修复 API Key。

修复后的分类规则和行为如下：

| 错误 | 运行层分类 | 是否适合原请求重试 | 用户动作 |
| --- | --- | --- | --- |
| 本地等待窗口耗尽 | `clientTimeout` | 可以有限重试 | 等待或缩小请求 |
| 502/504/524 | `upstreamTimeout` | 提纲阶段不重复原请求 | 缩小请求、切换模型或恢复 |
| 429 普通限流 | `rateLimited` | 可以退避重试 | 等待 |
| 429 并发/容量 | `concurrencyLimited` | 长退避后再试 | 等待账户并发释放 |
| 503 无可用渠道 | `providerUnavailable` | 不连续撞击同一模型 | 切换模型或渠道 |
| 403 余额/额度不足 | `quotaExceeded` | 不应反复重试 | 充值、检查配额 |
| 401 | `authentication` | 不应反复重试 | 检查 API Key |
| 上下文超限 | `contextLengthExceeded` | 不重复原 Payload | 压缩、分块或缩小输出 |

这里最关键的因果关系是：客户端超时和上游 504 不是一回事。客户端超时表示本地还没有得到响应就主动停止等待；504 表示中转站已经明确关闭请求。把本地超时从 240 秒改成 600 秒，不能让已经返回 504 的请求继续执行。

优化后的新问题是，不同中转服务对状态码和错误文本的表达不完全一致，所以分类只能是稳定的启发式边界，必须保留原始状态码、Provider code 和经过脱敏的短消息用于诊断；不能宣称任何中转站都能被完全准确识别。

### 28.8 第八阶段：提纲阶段连续 504 的定位与降载恢复

真实记录表明：同一个模型可以完成多个来源分块，却在最终提纲汇总处连续返回 504。原因不是模型完全不可用，而是两个请求的负载结构不同：

| 请求 | 输入结构 | 输出预算 | 风险 |
| --- | --- | ---: | --- |
| 来源分块提取 | 单个分块，来源范围明确 | 4,096 Token | 负载可控 |
| 最终提纲汇总 | 聚合后的完整知识账本 | 旧版最高 8,192 Token | 需要聚类、组织、分配证据并输出 JSON |

旧版在 504 后继续重试同一 Prompt。同一个上游网关会在相近时间再次关闭相同负载，五次重试只是把失败延长，没有改变失败条件。

本阶段的解决步骤是：

1. 将提纲输出上限收紧到 2,048 Token，并要求章节结构短小。
2. 将来源分块摘要及对应的 JSON 修复保留在 4,096 Token，避免证据 ID 和结构化摘要被截断；二者使用不同的等待窗口，JSON 修复为 180 秒。
3. 将直接提纲安全阈值从 24,000 Token 降到 3,000 Token，使章节阶段能够复用可加载的来源范围。
4. 对提纲 `upstreamTimeout` 禁止普通重试。
5. 立即构造精简知识账本：限制术语、事实、主题、冲突、开放问题和分块摘要的数量及单条长度。
6. 用精简账本进行一次 `deepNoteOutlineFallback` 请求，快速提纲输出上限为 1,024 Token。
7. 精简请求仍失败时，进入可恢复错误状态，不静默替换模型。

这次修复解决的是“失败后没有改变负载”的恢复缺陷，而不是保证所有 Provider 都能处理长请求。新的遗留边界是：如果中转站对所有非流式长请求都有固定的 60 秒网关限制，即使请求已经缩小仍可能 504；下一步才需要考虑内部流式接收并在本地聚合 JSON，不能继续无限增加重试次数。

### 28.9 第九阶段：章节阶段发现语义预算被错误重置

在分块和提纲都成功后，章节阶段曾出现：

```text
深度笔记语义调用预算已用尽（5/5）
```

这不是模型错误，而是运行层在提纲生成后重新创建了章节预算，把前面已经使用的分块分析调用和提纲调用丢失了。对于长对话，前面可能已经消耗了 3 至 5 次调用，章节阶段仍然按照新任务的固定初始额度计算，于是刚开始扩写就被预算门禁阻止。

修复方式是：

- `budget_for_drafting` 继承 `previous.semantic_calls_used`。
- 为每个选中章节预留首次生成加最多 5 次语义修订。
- 预算上限取“已有消耗 + 当前章节所需空间”的较大值。
- 人工恢复增加独立的恢复预算，不把自动重试和人工恢复混为一项。

这样修复后，预算不再提前耗尽；新的取舍是调用上限可能因章节数量增加而扩大，因此需要继续保留总量上限和人工恢复上限，防止异常提纲生成大量章节造成不可控费用。

### 28.10 第十阶段：失败、停止和暂停无法继续的问题

实际使用中，用户取消或任务失败后发现：

- 页面没有继续按钮。
- 失败 Run 的模型和阶段信息消失。
- 重新点击生成会提示已有可恢复任务。
- 任务中心找不到之前停止的任务。
- 重启应用后没有重新附着。

调查后确认这是前后端状态契约冲突，而不是单纯缺少按钮：

1. 后端 SQLite 中仍然保留 Run、章节、账本、事件和错误信息。
2. 前端收到 `error` 或 `cancelled` 后调用统一清理函数，清空了 Run 引用。
3. 数据库唯一索引仍将旧 Run 视为会话的可恢复任务。
4. 前端再次创建时既不能新建，也没有旧 ID 可以继续。
5. `cancelled` 原本没有纳入应用启动后的可恢复任务发现。

修复将操作拆成四种明确语义：

| 当前状态 | 操作 | 是否新建 Run | 处理方式 |
| --- | --- | --- | --- |
| `paused` | 继续 | 否 | 使用原检查点继续 |
| `cancelled` | 从检查点继续 | 否 | 保留已有来源、提纲和章节 |
| `error` / `blocked` | 重试失败步骤 | 否 | 清理失败章节和失败节点，完成章节不动 |
| `error` / `blocked` / `cancelled` | 重新生成 | 是 | 旧 Run 保留为诊断记录，新 Run 使用当前模型 |

人工恢复最多 5 次。每次恢复递增 `executionVersion`；达到上限后要求重新生成，避免同一个坏 Run 无限循环。

失败章节重置时同时处理两套状态：

- `note_pipeline_sections` 中的章节状态、正文、尝试次数、修订次数、证据和验证结果。
- `note_pipeline_nodes` 中的 DAG 节点状态、尝试次数、输出引用、验证结果和错误信息。

特别修复了 Serde 使用 camelCase 保存 `needsReview` / `needsRevision`，而旧 SQL 只匹配 snake_case，导致失败节点没有被真正重置的问题。

输入快照也增加一致性保护。继续旧 Run 前必须确认会话修订时间、消息 ID、附件 ID、附件内容哈希、文献 ID 和笔记 ID 没有改变；否则拒绝混合旧知识账本与新会话内容，并要求使用当前内容重新生成。

优化后的边界是：恢复只能保证状态和检查点正确，不保证 Provider 一定恢复。如果模型仍然返回 401、额度不足或固定 504，任务会再次进入明确错误状态，但用户不会再丢失失败位置和后续操作入口。

### 28.11 第十一阶段：模拟 E2E 验证本地链路，但不冒充真实模型测试

真实 Provider 受到外部凭据和渠道状态影响，无法稳定重复。因此新增仅在 `deep-note-e2e` Cargo feature 下编译的无窗口测试入口。它的边界经过刻意限制：

- 会话、SQLite、笔记、来源和事件全部写入隔离目录。
- 不读取正式用户数据库。
- 仅在 `MNEMORA_DEEP_NOTE_MOCK=1` 且测试特性编译时启用确定性模拟模型。
- 正式构建不包含可触发的模拟模型路径。
- 测试报告保存输入规模、来源覆盖、事件、预算、耗时和 Note ID。

第一份 16 条消息样本验证了：

- 3 个来源分块全部完成。
- 16/16 消息覆盖。
- 提纲、章节、验证、组装和 SQLite 持久化闭合。
- 语义调用 5/10。

第二份 24 条消息样本估算 58,352 Token，验证了更长输入：

- 5 个分块全部完成。
- 24/24 消息覆盖，遗漏 0。
- 提纲生成和确认成功。
- 1/1 章节完成。
- 语义调用 7/12。
- 来源记录 24 条。
- `contextCoverageCompleted`、`outlineReady`、`sectionCompleted`、`runCompleted` 等事件全部存在。

这里必须明确测试结论的边界：模拟模型返回的是确定性 JSON 和正文，它证明本地状态机、预算、恢复、来源追踪和持久化没有断裂；它不能证明真实模型写出的内容质量、真实 Provider 的响应速度、真实网关是否接受这些请求，也不能替代 Release 测试。

### 28.12 每次优化后仍然存在的问题和下一步

本轮并没有把所有问题宣称为已经解决，仍然存在以下明确边界：

#### 28.12.1 真实 Provider 尚未完成成功的 Release 全链路

当前真实渠道曾返回 401、403、429、503、504/524。错误已经能够被正确分类，但在有效 API Key、余额充足、模型渠道可用的条件下，还需要重新执行 16 条和 24 条样本，记录真实的：

- 每个阶段首字节等待时间。
- 每次请求的实际重试次数。
- Provider 返回的输入和输出 Token。
- 是否触发提纲精简恢复。
- 真实章节内容质量和证据引用准确性。

#### 28.12.2 模拟模型的提纲只有一个章节，不代表真实规划质量

为了保证 E2E 确定性，模拟模型返回一个最小合法提纲。这能验证管线闭合，却不能验证多章节 DAG 的并行性、依赖排序、章节选择和跨章节引用。后续需要增加多章节模拟场景：至少包含无依赖章节、存在依赖的章节、一个失败后重试的章节和一个已完成章节被保留的恢复场景。

#### 28.12.3 当前仍是完整会话数据模型，不是数据库级历史分页

本轮通过 Token 分块解决了模型请求过大问题，但会话存储和前端加载仍可能持有完整会话。它解决的是“发送给模型的范围”，不是“应用内存中永远只保留当前页面消息”。如果后续目标继续压缩 WebView 内存，需要单独实施消息分页、历史窗口加载、虚拟列表和 Rust/前端增量查询，不能把当前分块方案误认为已经完成内存分页。

#### 28.12.4 提纲阶段仍是本地聚合 JSON，不是完整的流式 JSON 聚合

当前优先采用缩小账本和降低输出预算解决 504。若真实 Provider 仍有固定网关时限，下一步需要：

1. 使用流式接口接收模型输出。
2. 在 Rust 端增量保存接收进度。
3. 在结束后进行 JSON 组装和结构校验。
4. 网络中断时保存已接收片段，但不能把不完整片段当成有效提纲。

该方案会增加流式解析、断点和清理复杂度，所以只有真实采样证明缩小请求仍不足时才引入。

#### 28.12.5 仍有少量 dead_code 警告

`ledger_analysis_prompt`、`agent_call_slots`、部分章节字段和兼容方法目前有编译器警告。它们不影响功能，但会降低后续维护时对真正问题的关注度。下一次整理应删除未使用函数，或补充实际调用和测试，避免长期保留“看起来可能有用、实际没有入口”的代码。

#### 28.12.6 当前报告文件受 `.gitignore` 规则影响

仓库原有 `.gitignore` 使用 `md/**/*.md` 忽略修改文档，因此新生成的测试报告可能在本地存在，但不会自动进入 Git 变更。这样适合避免把临时报告提交到仓库，却不适合要求“所有修复过程都可审计”的文档策略。后续应明确区分：

- 长期维护的修复复盘文档：强制纳入版本控制。
- 含本机路径、运行 ID 和临时耗时的测试报告：保留在本地或放入单独的诊断产物目录。

### 28.13 最终的因果闭环

本次问题的核心并不是“把超时时间改大”，而是三个相互连接的系统问题：

```text
请求负载没有被控制
  -> 中转站返回 504 / 上下文超限
  -> 通用重试重复相同 Payload
  -> 用户长时间看不到真实进展
  -> 取消无法穿透网络 Future
  -> 前端清理 Run 引用
  -> 检查点虽然存在，但用户无法继续
```

最终修复把它拆成了四个必须同时成立的条件：

1. **负载可控**：Token 预算、分块、精简账本和阶段输出上限限制单次请求。
2. **失败可分类**：区分本地超时、上游超时、并发、额度、渠道、认证和上下文错误。
3. **过程可观察**：请求级活动、持久化事件、阶段文案、重试等待和模型信息都来自真实运行状态。
4. **任务可恢复**：取消、暂停、失败和阻塞保留 Run、快照、账本、章节和事件，并提供继续、失败步骤重试和重新生成。

只有这四个条件同时存在，用户才不会把“上游已经返回 504”误认为“程序卡死”，也不会在点击取消后失去已经完成的工作。
