# 05 分阶段实施计划

> 前置阅读：`00`–`04`
> 本文把前四篇的实施项排成可执行顺序，给出每阶段的验收口径、回滚方案与测试补强。

## 1. 阶段划分与不可颠倒的理由

```mermaid
graph LR
    P0["P0 正确性与超时语义<br/>不做就持续产生坏数据"] --> P1["P1 容量与并发<br/>依赖 P0 的自适应控制器"]
    P1 --> P2["P2 文件系统化<br/>依赖 P0 的事务修复"]
    P2 --> P3["P3 检查点重构<br/>依赖 P2 的落盘能力"]
```

| 阶段 | 一句话目标 | 为什么不能提前 |
| --- | --- | --- |
| P0 | 停止产生坏数据、停止浪费墙钟 | — |
| P1 | 把 chunk 打包做安全 | 无自适应控制器时打包会放大 504（`00` 约束一） |
| P2 | 笔记变成目录 | 事务边界未修好时，跨介质写入的问题无法诊断（`00` 约束四） |
| P3 | 细粒度恢复与跨 run 复用 | 章节内检查点需要落盘目标（`00` 约束二） |

**与 doc 03 的分歧再次提示**：doc 03 把「打包 attachment chunk」列为 P0，本计划降为 P1。理由与依据见 `00` 第 5 节。

### 2.2 关键风险与回滚

**P0-7（流式保活）是唯一有外部不确定性的一项。** 部分中转站对流式与非流式的路由策略不同，个别上游可能不支持流式。必须做成 per-provider 开关，默认开启、失败自动回落非流式并记一次告警。回滚 = 关开关。

**P0-11/12（WAL）必须成对发布。** 只开 WAL 不改备份，会产出缺失最近事务的备份文件 —— 这是比不开 WAL 更糟的状态。若来不及一起做，先做 P0-12。

**P0-13 会打破现有测试假设。** 大量 store 测试依赖 `open_connection` 顺手建表。调整时逐个改为显式初始化，不要图省事保留 migrate 调用。

### 2.3 P0 完成的标志

- 人为在 Persisting 中断（例如注入 panic）后 resume，**只有一篇笔记**。
- 一次超时后，日志显示"缩小载荷"或"立即降级"，而不是 5 次 300ms 间隔的原样重投。
- 长生成（>120s）在中转站下不再出现 504。
- `PRAGMA journal_mode` 为 wal，且备份可恢复。

### 3.2 P1-5 的执行注意

打包本身不难，难在**目标值的选取**和**缓存失效的处理**：

- 目标值 = 控制器当前包线，**不是** 16000 token。实际值很可能明显更低。
- 切换时按 `03` 第 4 节 bump 缓存版本号（`chunk-digest-v2` → `v3`），并打一条 info 事件记录失效条数。不要让它静默全 miss（风险 R2）。
- 打包后单次失败损失变大，此时 P3 的章节内检查点还没做 —— 这是可接受的过渡态，但要在发布说明里记一笔。

### 3.3 回滚

P1-5 与 P1-3 用同一个开关控制（"保守分块模式"）。回滚 = 打开保守模式，chunk 回到每 100 行一个、预算回到固定 16000。缓存会再失效一次，这是回滚的已知代价。

## 7. 各阶段收益与代价小结

| 阶段 | 主要收益 | 主要代价 | 可回滚性 |
| --- | --- | --- | --- |
| P0 | 停止产生重复笔记；消除一类 504；不再把 25 分钟浪费在同一份大载荷 | 需要调整大量依赖 `open_connection` 建表的测试 | 高（逐项独立） |
