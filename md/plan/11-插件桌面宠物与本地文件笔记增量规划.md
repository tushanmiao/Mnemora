# Plan 11：插件体系、桌面宠物、本地文件转笔记与附件增量更新

> 文档性质：调研结论、架构决策、风险分析与分阶段实施计划。  
> 代码基线：Mnemora 提交 eb3abfe，应用版本 0.1.16，日期 2026-08-22。  
> GitHub 数据：通过 GitHub API 在 2026-08-22 获取的快照；真正接入前必须重新核验默认分支、提交、许可证、依赖和安全公告。

## 1. 先给结论：四个需求其实是一个问题

插件、桌面宠物、本地文件转笔记、附件增量更新看起来是四条产品线，真正共同的问题是：

> Mnemora 需要一个可治理的扩展边界，让外部能力可以被发现、安装、授权、执行、观测、更新、回滚和卸载，同时不能绕过来源、隐私、内存和恢复合同。

因此不建议先做任意第三方代码加载，而应先做声明式资源和宿主控制的能力：

~~~mermaid
flowchart LR
    A[Plugin Manifest] --> B[验证与信任分级]
    B --> C[Permission Broker]
    C --> D[Contribution Registry]
    D --> E[宿主 API]
    E --> F[Skill/Reader/Pet/Command]
    D --> G[事件总线]
    G --> H[任务状态与桌面宠物]
    F --> I[Source Unit]
    I --> J[附件增量 Recon]
~~~

第一阶段明确禁止第三方 DLL、EXE、安装脚本、隐式 Shell、任意路径读写和默认联网。需要执行代码时，优先考虑受限 WASM 或独立 Worker；即使使用 Worker，也必须有超时、取消、内存和输出预算。

## 2. 当前源码基线

### 2.1 已有能力

- Tauri 2、Rust、React/Vite；
- 固定 Tool Registry、Skill Repository、Manifest、版本和 Content Hash；
- Skill/Tool 渐进式披露，导入目录或 ZIP 时有 staging、路径越界和大小限制；
- 深度笔记 Rust 主管线：预检、输入快照、Reader/Vision、Source Chunk、Ledger、Planner、章节 DAG、检查点和恢复；
- 当前统一的深度笔记 Reader：read_attachment_text、read_pdf_pages、read_docx_blocks、read_xlsx_rows；
- 图片通过 Vision Source Chunk，代码文件按带行号的静态文本读取，不执行；
- PDF 文献库、页码、选区、批注、关联笔记和文献上下文 Chat；
- SQLite 任务、版本、事件和覆盖快照；
- ResourceRegistry、附件预览缓存、PDF Canvas Budget、任务中心。

### 2.2 仍然缺少的边界

1. 还没有第三方 Plugin Manifest、Marketplace、Permission Broker 和版本回滚闭环；
2. Skill 是提示和资源包，不是独立进程沙箱；
3. 本地文件格式注册表已能覆盖不少文本/代码格式，但还没有通用 DocumentElement 和统一导入入口；
4. 新增附件目前不能走附件级增量 Recon，只能在确认后完整重建；
5. 桌面宠物尚无独立窗口、资源包、事件订阅和设置；
6. 代码没有 AST、符号、import、调用图或项目级 DAG。

### 3.1 共同规律

1. Manifest 是发现、兼容和审计的唯一入口；
2. 扩展点由宿主定义，插件不能自创未授权的 IPC；
3. 元数据、资源、执行能力和权限分开声明；
4. 版本、许可证、来源 Commit、内容 Hash 和平台必须可追溯；
5. 开发安装与生产安装分开；
6. Marketplace 需要审核、灰度、撤回、兼容性和回滚；
7. 安装过程必须先 staging、校验，再原子切换。

## 4. Mnemora Plugin Manifest 与能力模型

### 4.1 建议的 Manifest

建议路径为 .mnemora-plugin/plugin.json。Manifest 只声明能力，不直接授予权限：

~~~json
{
  "schemaVersion": 1,
  "id": "com.example.reader",
  "name": "Example Reader",
  "version": "0.1.0",
  "publisher": "Example",
  "license": "MIT",
  "repository": "https://github.com/example/mnemora-reader",
  "sourceRevision": "40 位 Commit",
  "minMnemoraVersion": "0.1.16",
  "platforms": ["windows", "macos", "linux"],
  "components": ["skill", "documentReader", "petPack"],
  "contributes": {
    "skills": ["skills/reader/SKILL.md"],
    "documentReaders": ["reader.json"],
    "petPacks": ["pets/study-bird/pet.json"],
    "commands": ["reader.inspect"]
  },
  "permissions": ["attachments.read", "notes.read"],
  "activationEvents": ["onFileType:application/x-example"],
  "integrity": {"sha256": "包内容 Hash"},
  "runtime": {"kind": "declarative", "maxMemoryMb": 64, "timeoutMs": 5000}
}
~~~

校验规则：

- id 只能使用稳定的小写字符、数字、点和连字符，禁止路径穿越和相邻重复分隔符；
- schemaVersion、Mnemora 版本和平台先做兼容检查；
- repository、sourceRevision、license、integrity 缺一项就降为 Unknown；
- Manifest 不能声明宿主未注册的 contribution point；
- 权限是最小集合，不能使用通配符；
- 包内禁止符号链接、硬链接、设备文件和越界归档路径；
- 资源文件名、总大小、解压大小、文件数和目录深度都有上限。

### 4.2 组件分级

| 组件 | 第一阶段 | 说明 |
| --- | --- | --- |
| skill | 允许 | 只读方法论和提示正文，不执行脚本 |
| theme | 允许 | CSS/图标/颜色资源，经过净化 |
| pet-pack | 允许 | SVG/PNG/WebP、动画清单和许可证 |
| document-reader | 受限允许 | 只能输入统一 DocumentElement，宿主控制路径和预算 |
| command | 受限允许 | 只能调用宿主已注册命令 |
| tool | 后续 | 必须有 Schema、审批、超时、取消和结果预算 |
| provider | 后续 | 密钥、网络、数据出境需要单独审批 |
| native | 默认禁止 | 只有官方签名、审核和独立安装渠道才考虑 |

### 4.3 信任等级和权限

~~~text
TrustedOfficial      官方签名/审核、来源固定、资源完整
VerifiedCommunity    许可证、Commit、Hash、权限已审计
LocalDevelopment     开发目录，默认不自动激活
Unknown               只显示元数据，不执行高风险能力
~~~

建议权限：

| 权限 | 默认 | 风险 |
| --- | --- | --- |
| notes.read | 可申请 | 低 |
| notes.write | 每次确认 | 中 |
| attachments.read | 仅用户选择的附件 | 中 |
| library.read | 明确确认 | 中 |
| workspace.read | 关闭 | 高 |
| network.fetch | 关闭 | 高 |
| memory.read/write | 关闭 | 高/极高 |
| shell.execute | 第一阶段禁止 | 极高 |
| screen.capture | 第一阶段禁止 | 极高 |

Permission Broker 应把 pluginId、版本、会话、资源、动作、理由、有效期和用户决定写入审计事件。不能把“插件已安装”解释为“插件拥有所有权限”。

## 5. 安装、更新、回滚和卸载

~~~mermaid
sequenceDiagram
    participant U as 用户
    participant R as Registry
    participant V as Verifier
    participant S as Staging
    participant H as Host
    U->>R: 选择来源/版本
    R->>V: Manifest、许可证、Commit、Hash
    V-->>U: 信任等级与权限预览
    U->>S: 确认安装
    S->>S: 解压、路径、大小、资源校验
    S->>H: 原子激活
    H-->>U: 贡献点与状态
    U->>R: 更新
    R->>S: 安装新版本并保留旧版本
    S->>H: 健康检查
    H-->>S: 失败则回滚
~~~

必须满足：

- 下载和解压在临时目录完成；
- 校验失败不能污染当前版本；
- 新版本激活前运行 Manifest、资源、宿主 API 和最小 smoke test；
- 旧版本至少保留一个可回滚副本；
- 卸载前先停用事件订阅、销毁 Worker、释放资源和撤销权限；
- 事件记录 installStarted、verified、activated、failed、rolledBack、uninstalled；
- 更新不能静默修改已安装插件的权限集合，权限扩大必须再次确认。

### 6.2 产品定位

Mnemora 宠物是低打扰的学习与知识工作状态投影，不是第二个聊天窗口，也不是默认的屏幕监控器。

首版只订阅：

- 深度笔记：分析、等待确认、生成、修订、完成、失败；
- Chat Agent：思考、Tool 调用、等待审批、完成、失败；
- 英语：开始、连续学习、错题回流、掌握审计；
- PDF：打开文献、长时间阅读、批注保存。

默认行为：

- disabled；
- 无声音；
- 不录屏、不读麦克风、不读取其他窗口；
- 支持 quiet hours、全屏暂停、Reduced Motion、点击穿透和托盘关闭；
- 任务正文不直接显示在宠物气泡中，避免泄露敏感内容。

### 6.3 状态机和事件映射

~~~mermaid
stateDiagram-v2
    [*] --> Hidden
    Hidden --> Idle: 用户开启
    Idle --> Thinking: 任务开始
    Thinking --> Tooling: Tool/Reader 开始
    Tooling --> Thinking: Tool/Reader 完成
    Thinking --> Waiting: 等待确认
    Waiting --> Thinking: 用户确认
    Thinking --> Success: 成功
    Thinking --> Error: 失败
    Success --> Idle: 动画结束
    Error --> Idle: 用户关闭
    Idle --> Sleeping: 静默或空闲
    Sleeping --> Idle: 用户互动
    Idle --> Hidden: 用户关闭
~~~

事件只传递脱敏状态：eventType、taskId、phase、progressBucket、updatedAt、severity。不能把整段用户消息、附件路径、模型请求或 API Key 传给宠物资源。

### 6.4 窗口、资源和多屏

- 独立 Tauri 窗口：无边框、透明、可拖动、置顶可选、点击穿透可选；
- 保存显示器标识、逻辑坐标、DPI、缩放和窗口尺寸；显示器消失时回退到主屏；
- 关闭主窗口时销毁宠物窗口和订阅，不留下后台任务；
- 首版优先 SVG/CSS/PNG/WebP，限制帧数、像素面积、动画 FPS 和解码字节；
- 每个 Pet Pack 必须有 manifest、preview、LICENSE、NOTICE 和 content hash；
- 资源加载走 ResourceRegistry，离屏动画暂停，长期空闲进入静态帧；
- 把宠物资源纳入内存 Benchmark 和插件资源账本。

## 7. 本地文件生成笔记：统一入口而不是再造第二条管线

### 7.1 目标链路

~~~mermaid
flowchart LR
    A[文件/图片选择] --> B[安全预检]
    B --> C[格式适配器]
    C --> D[DocumentElement]
    D --> E[Source Chunk/定位]
    E --> F[Ledger]
    F --> G[Planner]
    G --> H[用户确认]
    H --> I[章节 DAG/Writer]
    I --> J[Evidence/验证]
    J --> K[笔记与来源原子保存]
~~~

应复用现有 Deep Note Pipeline。不要为文件笔记另建一套不兼容的 Planner、Writer 或 DAG。

### 7.2 首期格式矩阵

| 类型 | 当前/目标 Reader | 来源定位 | 可靠性边界 |
| --- | --- | --- | --- |
| .md/.markdown | Text | 行号、标题、代码块 | Markdown 结构可保留；需防止嵌套 Mermaid |
| .txt/.rst/.adoc | Text | 行号 | UTF-8 优先，编码失败明确报错 |
| .py/.ts/.rs 等代码 | Text + Code 元数据 | 文件、行号、语言 | 静态读取，不执行；没有 AST/调用图 |
| .json/.yaml/.toml/.sql 等 | Text | 行号/键路径（后续） | 不把配置值当秘密；敏感文件门禁 |
| .docx | DOCX blocks | 块序号、表格 | 块序号不等于页码；复杂布局可能丢失 |
| .xlsx | XLSX rows | Sheet、行、单元格 | 不重算公式；工作表和大表需分页 |
| .pdf | PDF pages | 页码、文本层 | 当前无 OCR；扫描件、多栏和复杂表格低置信 |
| 图片 | Vision Source | 附件 ID、视觉描述 | 只描述可见内容；模型必须明确支持 Vision |

统一 DocumentElement 建议：

~~~text
documentId / attachmentId / elementId
elementType: heading | paragraph | table | code | image | formula | sheetRow
content
sourcePath / pageNumber / blockIndex / lineStart / lineEnd
sheetName / cellRange / boundingBox
contentHash / parserId / parserVersion / confidence
~~~

### 7.3 Python 等代码文件如何处理

当前正确答案不是把 .py 当可执行工具，而是：

1. 按行、带文件名和语言标签读取；
2. 每个 Source Chunk 保存起止行和内容 Hash；
3. Prompt 明确“仅静态分析、未执行、不能推断运行结果”；
4. 对跨文件关系标记为未知；
5. 后续可增加 Tree-sitter 解析、符号表、import 图和项目 DAG，但这些必须是独立的只读 Worker，有解析版本和超时预算。

## 8. 附件级增量更新：为什么现在不能直接做

当前纯文本 noteEdit 已有“计划 → 补丁 → Diff/确认 → 原子应用”链，但新增附件没有完整的 Reader/Vision → Source Chunk → Evidence → Ledger → Patch 链。若只推进消息锚点，会把未读取附件错误地标成已覆盖，这是来源欺骗而不是优化。

### 8.1 Source Unit 合同

~~~text
id
conversationId
messageId
kind: body | attachment | literatureSelection | noteSelection
attachmentId
contentHash
parserId
parserVersion
status: pending | extracted | covered | failed | unsupported
elementIds / chunkIds / evidenceIds
createdAt / updatedAt
~~~

### 8.2 差异分类

~~~mermaid
flowchart TD
    A[旧 Coverage Snapshot 与当前来源] --> B{变化分类}
    B -->|无变化| C[Up to date]
    B -->|仅新增正文| D[文本增量]
    B -->|新增附件| E[附件 Source Recon]
    B -->|旧附件 Hash 变化| F[完整重建或人工重审]
    B -->|删除来源| G[影响分析与确认]
    B -->|Parser 版本变化| H[失效旧解析缓存]
    B -->|敏感/不支持| I[明确阻止]
~~~

判定规则：

- 新消息 D 不属于已冻结的旧 Run；它只能进入下一次更新；
- 新增附件只读取一次，内容 Hash 和 parserVersion 写入 Source Unit；
- 旧附件 Hash 变化不能直接局部 Patch，除非影响分析证明所有引用仍有效；
- 删除或替换附件会使关联 Evidence 失效，至少触发受影响章节重审；
- 核心定义、数字、时间线、全局结论或多章节依赖被影响时，必须完整重审；
- 任何 Reader/Vision 失败都不能推进 Coverage Snapshot。

### 8.3 目标增量链路

~~~text
冻结当前来源
→ 比较 Source Unit
→ 只读新增/变化附件
→ 生成增量 DocumentElement、Chunk、Digest
→ 合并 Ledger 与 Evidence
→ 计算受影响章节和 requiresGlobalReview
→ 生成 Note Update Proposal
→ 展示 Diff、来源和风险
→ 用户确认
→ 一个事务推进 Note、Sources、Coverage、Version 和 Proposal
~~~

建议新增表：

- note_source_units；
- note_incremental_runs；
- note_update_proposals（扩展 impact、requiresGlobalReview、sourceUnitIds）；
- note_parse_cache（attachmentHash + parserId + parserVersion + optionsHash）。

### 8.4 幂等和崩溃恢复

每次输出应使用稳定幂等键：

~~~text
runId + targetNoteId + sourceSnapshotHash + planVersion + operation
~~~

事务内同时写入：

1. 新版本或补丁结果；
2. 来源和 Evidence；
3. Coverage Snapshot；
4. 输出 Ledger；
5. Proposal 状态；
6. 输出幂等记录。

重启时先查幂等记录，再决定重放、继续或跳过；不能只依赖 React 状态或最后一个事件。

## 9. 分阶段实施

| 阶段 | 交付 | 难度 | 主要风险 |
| --- | --- | --- | --- |
| P11.1 | Manifest、Registry、信任等级、权限预览、Skill/Theme/Pet 声明式包 | 中高 | 权限模型过早膨胀 |
| P11.2 | MD/TXT/代码/DOCX/XLSX/图片统一 DocumentElement 入口 | 高 | 解析器差异、来源定位 |
| P11.3 | Pet MVP：独立窗口、状态映射、设置、资源预算 | 中高 | 多平台窗口行为和常驻内存 |
| P11.4 | Source Unit、Coverage Snapshot、parser cache | 高 | 数据迁移和旧笔记兼容 |
| P11.5 | 新增附件增量 Recon、影响分析、Proposal、原子应用 | 很高 | 局部更新误伤全局结论 |
| P11.6 | 签名 Marketplace、Worker/WASM、灰度、回滚和供应链扫描 | 很高 | 执行代码的安全与运维 |

推荐先做 P11.1 + P11.4 的合同，再做体验层 P11.2/P11.3。没有 Source Unit 和权限边界，插件与宠物越快上线，后续迁移成本越高。

## 10. 验收与否决条件

### 验收

- Manifest、版本、许可证、来源 Commit、Hash 和平台可审计；
- 安装失败不污染现有版本，更新失败自动回滚；
- 插件不能访问未授予的文件、网络、记忆或 Shell；
- 宠物默认关闭、无声音、支持 Reduced Motion、静默时段、多屏和销毁；
- MD/TXT/代码/DOCX/XLSX/PDF/图片均能显示真实来源定位和置信度；
- 新增附件只读新增 Source Unit，旧附件替换触发重审；
- Proposal 拒绝不改变笔记、来源或 Coverage；
- 取消、重启、崩溃和重复提交不会产生重复输出；
- 资源、Worker、Canvas 和宠物窗口在关闭/取消后可回收。

### 上线否决

- 未知插件默认取得 Shell、工作区或屏幕权限；
- 模型未读取附件却推进覆盖快照；
- 宠物默认录屏、监听麦克风或上传原文；
- AI 补丁无 Diff、旧 Hash 和用户确认；
- 解析器升级却继续使用未知版本缓存；
- 新附件被静默忽略或被错误纳入旧 Run；
- 崩溃重试产生重复笔记或覆盖用户手工修改。

## 11. 仍需产品决策的问题

1. Marketplace 是官方索引、Git URL，还是两者并存？
2. 是否接受用户本地开发插件？若接受，是否必须显式开启开发模式？
3. Pet Pack 是否允许第三方动画脚本，还是永远只允许声明式动画？
4. 新附件增量默认更新原笔记，还是总是先生成独立 Proposal？
5. 旧附件删除后，是否允许保留无来源的 AI 补充内容？
6. Tree-sitter/复杂 PDF/OCR 是否内置，还是作为受限 Reader 插件？

> 最终原则：先建立统一的 Manifest、Permission、Source Unit、Evidence、Resource 和 Recovery 合同，再扩大插件、宠物和格式生态。任何扩展都不能绕过 Mnemora 的来源、权限、内存和恢复边界。
